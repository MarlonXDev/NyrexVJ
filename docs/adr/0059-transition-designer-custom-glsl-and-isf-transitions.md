# ADR 0059: Transition designer: deck transitions of your own as GLSL or ISF files

- **Status:** Accepted for the file based transitions, requested by MarlonXDev (2026-11-27 20:32, prompt 37): extend the deck transitions with transitions of your own (GLSL or node based) with parameters, a preview, saving and loading and safe fallbacks, without changing the existing ones. Node based transitions are an **open question for the maintainer** (see below). Issue [#148](https://github.com/MarlonXDev/NyrexVJ/issues/148).
- **Date:** 2026-11-27
- **Owners:** Maintainers (pending assignment)
- **Related:** [SHADERS.md](../SHADERS.md), [ADR 0030](0030-isf-import.md) (ISF import), [ADR 0054](0054-resoport-glass-effects-transitions-and-minimized-output.md) (the 15 built-in transitions), [INTERFACES.md](../INTERFACES.md), [TESTING.md](../TESTING.md)

## Context
- State at main `9459e07`: 15 built-in transitions (Fade to Frost) live in one fragment shader in `src/render/engine.cpp` that picks the look with `uniform int uType`. `Engine::switchDeck` starts a transition when the length is at least 0.05 s: with one already running it copies what is on screen into the first deck target and freezes it, so a new switch fades from the picture you see. `Engine::render` draws the old deck into `deckTex_[0]` (or keeps the frozen picture), the new deck into `deckTex_[1]`, and `transitionPass` mixes them into the output. The picture of a deck is opaque at that point, so a transition never sees alpha. The buffers of the old deck are held by its feedback set and released after the transition.
- The deck settings hold the type as a number, a length in seconds or beats, beat sync and auto cycle. They are saved with presets and the session.
- The ISF reader refused transition files (`startImage` and `endImage`). The shader plan machinery (`#pragma nyrexvj ...`, controls, passes, channels) already compiles clips and image filters, and the engine already has `runShaderPasses` for them.

## Decision
1. **A transition is a shader file, found the way a filter is.** `#pragma nyrexvj transition` (or an ISF file with `startImage` and `endImage`) marks the plan as a transition. It is listed in the transition lists as `Transition: <file stem>`, not in the Library and not in the effect list. No second GLSL runtime and no second editor: the file goes through `prepareShaderSource`, the plan, `planPassFragmentSource` and `runShaderPasses` like every other shader, and it is edited in the shader editor of 0.46.0.
2. **What the file sees.** Two new channel sources, `from` and `to`, are bound to channels 0 and 1 and are implied by the pragma (no `channel` lines needed). The header adds `uniform float uProgress`, `uFrom`, `uTo`, `colFrom(uv)` and `colTo(uv)`. `uProgress` is the plain progress of the switch from 0 to 1, not eased: the built-in transitions ease inside their own shader, so a file decides itself. The five names are reserved.
3. **Limits that keep it safe.** One image pass, no buffers, no media, no `picture`, no `alpha`, no `filter`; the result leaves with alpha 1 whatever the file writes (the wrapper `main` forces it). At most 32 transition files are listed, a file over 256 KiB is refused like any shader. ISF transitions are refused when they have only one of the two pictures, an `inputImage` next to them, imported pictures or passes with a `TARGET`.
4. **Controls.** `param` lines work as in a clip. The values live in `DeckSettings::transitionValues` (16 numbers, `null` = default of the file) and are resolved against the plan when a switch starts; they are saved with the deck settings. The controls are drawn by the same function that draws the controls of a clip.
5. **Choosing and saving.** The transport bar and the Trigger window list the built-in transitions and then **Your transitions**. `DeckSettings::customTransition` holds the name; the built-in `transition` number stays next to it and is the fallback. JSON keys `customTransition` and `transitionValues` are written only when a file is chosen (the values only when one was changed), so every earlier preset, session and fixture is written byte for byte as before (the frozen files of `nvj_compat_tests` did not change). A name that does not start with `Transition: ` or is longer than 96 bytes is dropped on load.
6. **Runtime.** `Engine::ensureCustomTransition(name)` compiles the plan once per version of the file (the library bumps the version when the file changes) and keeps the programs in a map; the deck setting is looked at every frame while no transition runs, so the program is ready before the first switch. `customTransitionPass` runs the plan into the output with the outgoing picture as the picture and the incoming picture as the second picture. A switch while a transition runs is untouched: the freeze logic is above the pass and does not know which kind of transition it feeds.
7. **Fallback.** If the name is not in the library, the file is gone, is no longer a transition, has a mistake or does not compile, `ensureCustomTransition` returns false, the error is kept for the interface and the built-in transition stored next to the name runs. A running transition whose file changes goes on with the new version from the next frame, or with the built-in one if the new version is broken. A repaired file is picked up while the program runs.
8. **Preview.** `Engine::requestTransitionPreview` renders a custom or built-in transition at a chosen progress into a 160 x 90 target, between the clip pictures of Plasma and Tunnel (the thumbnails the engine already keeps). It is drawn only while the Trigger window asks for it and costs one small pass.

## Measured
All values come from `nvj_transition_tests` and `NyrexVJ --shader-selftest` on Linux with Mesa llvmpipe (software OpenGL, 1280 x 720, one machine, not a graphics card). The times are wall clock per frame in milliseconds and include the CPU rasterisation; two runs agree within about 3 ms, so differences smaller than that are noise.
- Unit tests: 78 checks (`nvj_transition_tests`).
- Render tests: 42 new checks, all passed: start and end on the right deck, a hard wipe in the middle (new deck left, old deck right, progress 0.5), `uProgress` blending (127, 0, 128 at the middle), a control with its default and a stored value, a switch during a running custom transition (the centre moved from (149, 106) to (151, 104) in one frame and the deck that was asked for is reached), six quick switches, a change to a built-in transition during a custom one, a compile error, a deleted file, an unknown name, a repaired file, a deck with a layer with alpha 0.5 (starts from (124, 8, 123, 255), opaque in the middle and at the end), a transition that writes alpha 0 (still alpha 255), a deck with feedback buffers (the old deck keeps its buffers while it fades out, they are released afterwards), the preview at progress 0, 0.5 and 1 (0, 128, 255), and the 15 built-in transitions next to them.
- Frame time while one deck plays: 16.5 ms. While a transition runs both decks are drawn, so the baseline for a transition is two decks: built-in Fade 41.6 ms and 40.9 ms in the two runs, built-in Radial 40.9 and 41.3, custom cross mix 38.7 and 38.5, custom iris 43.0 and 42.2, a custom shader with sixteen taps from each picture 74.9 and 78.0. A custom file of the same cost as a built-in one costs the same; what a file does with its taps is what it costs.
- The first frames (second run): the worst of the six frames after choosing a transition, when the program is prepared, is 17 to 20 ms for the three custom files and 16 to 20 ms for the two built-in ones. The worst of the three frames after the switch is 44 ms for the two light custom files and 86 ms for the sixteen-tap one (its normal frame is 75 to 78 ms), against 47 and 55 ms for the built-in ones. So there is no extra stall for a new file on this driver. A real driver can take longer to link a new program; that was not measured.
- Memory: a custom transition draws into the same targets as the built-in ones and adds no picture sized target. The preview adds one 160 x 90 target (57,600 bytes). One compiled program is kept per file that was used (the size depends on the driver and was not measured), at most 32 files.

## Not done
- **Node based transitions** (below).
- More than one pass, buffers or media in a transition, a transition that reads the alpha of a deck (the picture is opaque there), a transition that reads the audio, and a transition that runs on a single layer instead of the deck.
- A different default for new decks, or a new built-in transition. The 15 built-in ones are untouched.
- Moving the controls of a transition with audio, LFOs, MIDI or OSC; they are set by hand in the Trigger window like the controls of a clip.
- A transition list that is part of a preset pack or of a show package: the name is stored, the file is not. A deck whose file is missing on another PC uses the built-in transition and shows the message.
- A transition shown in the preview with your own clips; the preview uses Plasma and Tunnel.
- A transition file that changes while a transition runs was not tested during the run: the code looks at the version of the file every frame, so the next frame should use the new version, but only a change between two switches is tested.
- Beat synced lengths were not tested separately with a custom file; the length is worked out before the type is looked at, so both kinds use the same code, but no test sets Beat sync with a custom transition.

## Open question for the maintainer: node based transitions
The node editor builds effects from 68 nodes into one GLSL function with the input nodes `Picture` (`texture(uTex, uv)`) and `Previous`. Prompt 37 asks for "user-defined GLSL or node-based transitions". The GLSL half is built. For the node half the proposal is small, but it changes the node format and the catalogue, so it needs a decision:
- Two new input nodes, **Incoming Picture** (`texture(uTo, uv)`) and **Transition Progress** (`uProgress`), and a flag in the node file that marks a graph as a transition. `Picture` would be the outgoing picture. The compiler would wrap such a graph with the same header as a transition file, so everything above (list, controls, fallback, preview) would apply unchanged.
- Cost: two nodes and a flag in the file format (a new version of `.nyxnode` that older programs would refuse or ignore), an entry in the catalogue test, and the editor needs a preview with two pictures.
- Risk: an effect graph that uses the new nodes outside a transition has no incoming picture; the proposal is that these nodes then return the picture and 0, so nothing breaks.
- Not started, because it changes the format of files people share. Say yes or no, or whether the nodes should have other names.

## Consequences
- `DeckSettings` has two new fields; the preset and session JSON gain two optional keys, older programs ignore them, and a file without them is read as before.
- `ShaderInputKind` has two new values and `ShaderPlan` a flag; a plan that is not a transition is unchanged (the fingerprint test of the generated source of old shaders did not change).
- The clip library now skips transition files like filter files (a transition that cannot be read stays in the Library with its message, as a broken filter does).
- Not run on a real graphics card or on Windows beyond the CI build; see `M-TRN-1`.
