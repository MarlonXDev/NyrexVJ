# ADR 0021: DXV videos are converted to HAP in the background, and FFmpeg can be set up with one button

- **Status:** Accepted (2026-11-21, requested by MarlonXDev), implemented in v0.28.0. Issue [#68](https://github.com/MarlonXDev/NyrexVJ/issues/68).
- **Date:** 2026-11-21
- **Owners:** Maintainers (pending assignment)
- **Related:** [MEDIA.md](../MEDIA.md), [FFMPEG.md](../FFMPEG.md), [ADR 0010](0010-video-decode-pipeline.md), [ADR 0019](0019-dxv-software-codecs.md), [PERFORMANCE.md](../PERFORMANCE.md)

## Context
ADR 0019 kept the processor decoder for DXV and said that anyone who needs a low processor load can convert a clip to HAP by hand with `ffmpeg`. The request for this change asks NyrexVJ to do that itself: recognise DXV Normal Quality and High Quality, with and without alpha, convert them to HAP, HAP Alpha or HAP Q in the background with a progress display and a cancel button, keep resolution, frame rate, transparency and correct colours, never change the original, cache the result, play it through the existing HAP pipeline, fall back to the DXV playback when anything fails, and measure and test all of it. The conversion needs FFmpeg with a DXV decoder, a HAP encoder and the MOV muxer, so the request also asks for a check of those at program start, an installation by button press from a trustworthy source with checksum and licence checks, on Windows and Linux, without touching an existing installation and without installing anything the person did not agree to. The goal behind all of it: as little processor, graphics card and video memory load as possible, above all next to VRChat.

## Findings (what existed before)
- **DXV decoding:** FFmpeg's `dxv` decoder, software only, used as a normal video decoder (ADR 0019). Four variants by the texture tag in the first packet: `DXT1` (Normal Quality), `DXT5` (Normal Quality with alpha), `YCG6` (High Quality), `YG10` (High Quality with alpha). Normal Quality arrives as RGBA, High Quality as planar YUV in the YCoCg colour space.
- **HAP on the graphics card:** NyrexVJ has its own HAP container parser (`src/media/hap.cpp`: Snappy, chunks, uncompressed) and uploads the compressed blocks directly (`DecodePath::HapGpu`): DXT1 for HAP, DXT5 for HAP Alpha, DXT5 with a YCoCg shader for HAP Q. No processor decompression of the picture, 0.5 or 1 byte per pixel in video memory instead of 4.
- **Alpha:** HAP Alpha carries alpha in the DXT5 texture. **HAP Q with alpha ("HAP Q Alpha", two textures) is not supported**, neither by NyrexVJ's parser and shaders nor by FFmpeg's `hap` encoder (`hap`, `hap_alpha`, `hap_q` only). This was checked in the code, not assumed.
- **FFmpeg loading:** `ffmpeg_dyn.cpp` loads the five libraries at run time from a list of folders that already contained the NyrexVJ data folder (`ffmpeg`). Nothing could download or verify a build.

## Decision

### Conversion
1. **Decode with FFmpeg, encode with FFmpeg's HAP encoder, write MOV.** `src/media/hap_convert.cpp` reads the DXV file, decodes every frame, converts it to the format the HAP encoder wants (YCoCg frames are converted with full range, the same arithmetic as the shader) and writes `<key>.mov`. The original file is only opened for reading.
2. **Variant to target.** DXT1 becomes HAP, DXT5 becomes HAP Alpha, YCG6 (High Quality) becomes HAP Q, YG10 (High Quality with alpha) becomes HAP Alpha, an unknown tag becomes HAP Alpha (the safe format that keeps alpha). A format chosen in Settings (`convertFormat`: automatic, HAP, HAP Alpha, HAP Q) is used only when it keeps the picture as it is: a video with transparency never becomes HAP or HAP Q. **HAP Q with transparency is not offered** because it is not supported (see Findings).
3. **Resolution, frame rate, transparency, colours.** The converter keeps the size (and refuses sizes HAP cannot store, such as a size that is not a multiple of 4 or above 8192 pixels, with a message instead of a distorted copy), the frame count and every presentation time, and the alpha channel. After writing, the copy is read back and compared with the source (frame count, size, HAP codec); a copy that fails this check is deleted and the original keeps playing.
4. **Background, progress, cancel.** One worker thread with a lowered priority (`platform::setCurrentThreadBackground`) converts one video at a time; the decoder and the encoder use at most two threads. Progress is reported per frame and a cancel flag is checked between frames. A cancelled or failed conversion removes its partial file.
5. **Import mode.** Settings, Performance, Convert DXV videos to HAP: Off (never converts), Ask (default: a notice card lists the DXV videos it found and waits for the answer, Not now is remembered per file), Automatic (converts every DXV video it finds). Default is Ask because converting uses disk space and processor time and the person did not agree to it yet. Only `.mov` files are probed, in the clip library and after an import.
6. **Cache.** `<user data folder>/cache/hap/`, one `<key>.mov` and one `<key>.meta` per source. The key is the first 32 hex digits of the SHA-256 of a fingerprint (file size, the first and the last MiB of the file) plus a tag with the converter version, the format and Snappy, so a renamed or moved file finds its copy again, an edited file does not, and a new converter version or setting makes a new copy. Entries are written to a `.part` file and renamed. A size limit (default 4 GiB, 256 MiB to 200 GiB) evicts the entries that were used longest ago first, bad entries before good ones and never one that is playing or was just created. Settings, Performance has Clear cache and Open cache folder.
7. **Playback and fallback.** `MediaPlayer` asks the manager for a converted copy when a clip starts (`video_redirect` hooks, so the render code does not depend on the manager) and plays it through the normal HAP pipeline. While a copy is being made the DXV original plays, and the copy takes over by a hot swap as soon as it exists (the new decoder is opened asynchronously and swapped in at a frame boundary). If the converted copy cannot be opened, fails to decode or the hot swap fails, the cache entry is marked bad (it is not offered again) and the original DXV keeps or resumes playing; the clip status shows when a converted copy is in use.
8. **Measuring and tests.** `NyrexVJ --bench-convert RUNS:file1,file2 [--convert-format ...] [--convert-keep DIR]` (no window) measures conversion time, decode and encode time, frames per second, the factor against playback speed, the size ratio and the process CPU time; `scripts/bench_video.py --dxv FILE` plays the original and its converted copy through `--bench-video` and prints both tables. `tests/test_convert.cpp` (new target `nvj_convert_tests`, 413 checks) covers the cache, the settings tag, the manager (modes, queue, cancel, eviction, bad entries, restart, duplicate content, a real conversion), the variant detection and the target choice; `tests/test_media.cpp` covers the converter on the real DXV file (DXT1) and on stand-in files for the other variants.

### FFmpeg setup
9. **Check at start.** A capability check runs on its own thread shortly after the window opened: are the libraries compiled in and loadable, is there a DXV decoder, does the HAP encoder work (all three variants are tried with a small test picture), is the MOV muxer there, is Snappy available. The result is shown in Settings, Performance and drives the notice card; the conversion is switched on only when everything is there.
10. **One button, never automatic.** Download and set up FFmpeg in Settings, Performance. Nothing is downloaded before the press, and not because of an update, a new video or a setting. The notice card only opens the settings page.
11. **Source and checks.** The release `latest` of BtbN/FFmpeg-Builds on GitHub over HTTPS (a fixed address prefix, the shared LGPL builds for FFmpeg 8.1 and 9.0 by the avcodec major number NyrexVJ was built for; avcodec 60 and 61 have no ready-made build, the message says so). The SHA-256 comes from the `checksums.sha256` of the same release and must match the download. The archive is unpacked by NyrexVJ's own reader (zip, and tar.xz through a run-time `liblzma`) with limits and with rules against paths that leave the folder, links, encryption, and too many or too large entries, and only the five libraries and `LICENSE.txt` are taken out. The `LICENSE.txt` must be the LGPL text and the configuration string inside `avutil` must exist and must not contain `--enable-gpl` or `--enable-nonfree`. Any failure removes the temporary files and installs nothing.
12. **Where, and what is left alone.** Into the `ffmpeg` folder of the NyrexVJ data folder via a staging folder and a rename (an existing folder is renamed to `ffmpeg.previous` and put back if the move fails), with `NYREXVJ_FFMPEG.txt` recording version, address, hash and licence. System installations and other folders are never written. Windows and Linux (x64 and ARM64 by the package name; the ARM64 packages are untested), with WinHTTP on Windows and `libcurl.so.4`, loaded at run time, on Linux (the same loader the updater uses). It needs about 700 MB of free space while it works and shows progress per step, can be cancelled and shows errors in the person's language.
13. **Manual alternative.** The same section has Set up by hand: the exact folder, the exact file names, Open FFmpeg folder and Check again.

## Alternatives
- **An own DXV decoder with a direct DXT upload.** Still rejected, for the reasons in ADR 0019 (no specification, LGPL only reference, derivative work). Conversion removes the processor cost for the person without touching that.
- **Convert with the `ffmpeg` command line program.** Rejected: NyrexVJ would depend on a program in `PATH`, would have to parse its output and could not report progress or cancel cleanly. The libraries are already loaded.
- **Convert inside the render loop or on the render thread.** Rejected: conversion of a long 4K clip takes minutes; it runs on a low-priority worker.
- **Convert automatically without asking.** Rejected as the default: it uses disk and processor without consent. It stays available as the Automatic mode.
- **Pin a SHA-256 per FFmpeg build in the program.** Would defend against a compromised release, but the BtbN release `latest` changes with every build, so every build would need a NyrexVJ release. Not done; the limit is stated in [FFMPEG.md](../FFMPEG.md). A frozen, versioned release with a pinned hash can replace it later.
- **Download FFmpeg from the system package manager or install it system-wide.** Rejected: it needs elevated rights, would touch existing installations and differs per distribution.
- **HAP Q Alpha.** Not implemented: neither the parser and shaders nor FFmpeg's encoder support it, and nothing was invented to pretend otherwise.

## Consequences
- A DXV library can be converted once, and later playback runs on the HAP path: no processor decode of the picture, 0.5 to 1 byte per pixel in video memory instead of 4 (measured on the 128 x 72 test clip: 9,216 bytes against 73,728, see [MEDIA.md](../MEDIA.md)).
- The conversion costs disk space (a HAP copy is about as large as the DXV file for DXT1 and larger for HAP Q, measured 1.09x and 1.96x on the test clip) and one pass of processor time per video, on a worker with lowered priority.
- The converted copy is a second lossy generation (DXT1 to DXT1 is nearly lossless, measured mean error 0.19 of 255, worst 4; HAP Q 1.05, worst 11; the real High Quality and alpha paths were not measured on real files).
- NyrexVJ now contains code that downloads and unpacks an archive. It is limited as described, but it is a new attack surface that reviewers should look at (`src/media/ffmpeg_setup.cpp`, `src/core/archive.cpp`, the two `httpDownload` implementations).
- `docs/DEPENDENCIES.md` lists the new run-time libraries (`libcurl.so.4` for downloads of any kind, `liblzma.so.5` for tar.xz). Both are optional.

## Validation / open questions
- **Real DXV files.** Only one real DXV file was available, a 128 x 72 DXT1 clip of 12 frames. DXT5, High Quality and High Quality with alpha were tested with stand-in files (other codecs with the same pixel layout, a file with the YCoCg tag, ProRes with alpha) and with the tag detection on synthetic packets; whether real High Quality and alpha files convert with correct colours and alpha was not verified. Please report wrong colours.
- **Performance at real sizes.** The only DXV measurement is the 128 x 72 clip (decode 0.10 ms per frame against 0.04 ms for the HAP copy, video memory 73,728 against 9,216 bytes, in a headless run with a software rasteriser). It shows the direction and that the pipeline works, not the effect at 1080p or 4K. `--bench-convert` and `scripts/bench_video.py --dxv` measure real files on your computer. Nothing was measured on a real graphics card, in VR or next to VRChat.
- **Windows.** The Windows download (WinHTTP) and the loading of the installed DLLs were compiled (MSVC in CI) but never run on Windows. The real Windows `zip` archive of the release was installed by the archive code on Linux. The Linux download ran end to end through `libcurl` (66 MB, checksum, unpacking, licence, install, loading) in `nvj_convert_tests`.
- **Trust.** The checksum protects against damage and wrong files, not against a compromised release (see above).
- **Hot swap and fallback** were tested with unit tests and the manager, the redirect and the settings, and the full playback was run with the benchmark; the swap while a clip is on screen in the interactive program, the notice cards and the settings page were drawn and compiled but not used by hand in a window.
- **Copy of the same content at two paths** is converted once and found by content, but the manager keeps one source path per cache entry, so the second path is offered again at the next start and then resolved as already converted.
