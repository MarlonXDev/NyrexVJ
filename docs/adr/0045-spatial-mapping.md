# ADR 0045: Optional 3D mapping onto real surfaces with a virtual projector, a viewer camera and a manual calibration

- **Status:** Accepted for the automated part (requested by MarlonXDev as prompt 25). Issue [#118](https://github.com/MarlonXDev/NyrexVJ/issues/118). Nothing was run with a real projector, a real room, two real projectors or a real graphics card. Automatic calibration with a camera is not built.
- **Date:** 2026-11-26
- **Owners:** Maintainers (pending assignment)
- **Related:** [OUTPUTS.md](../OUTPUTS.md), [manual chapter "3D mapping"](../manual/manual.en.md), [INTERFACES.md](../INTERFACES.md), [KNOWN_ISSUES.md](../KNOWN_ISSUES.md), [TESTING.md](../TESTING.md), [ADR 0015](0015-advanced-output.md), [ADR 0023](0023-advanced-output-2.md)

## Context
An output slice could only be a flat picture with four corners, a warp grid, a mask and edge blending. That is enough for a screen, but not for a pillar, a box or a wall that the projector hits at an angle, because there the corners have to be worked out by hand for every projector position. The prompt asked for an optional model of the real surfaces, a virtual projector and viewer, calibration points, perspective projection and a manual calibration with test patterns, without touching 2D venue files, and for hardware auto-calibration only as a separate later phase.

## Findings (what existed before)
- **Existed:** up to four output windows with up to eight slices each, a mesh per slice with corner perspective and a warp grid up to 17 x 17, masks, edge blending, colour, a test pattern, venue setups as JSON with versioned and compatible keys, an output memory budget with an estimate that matches the measured memory, and a self test of the real output window with pixel checks against a CPU model.
- **Not found:** any 3D model of a room, a pose of a projector, a lens model, a depth test in the output window, a way to find a projector pose from known points, or a camera-view picture source.
- **Not verified before this version:** perspective from a projector pose, lens shift conventions, behaviour of overlapping projectors in space.

## Decision
1. **One optional block per slice.** A slice gets a switch **Use 3D mapping for this slice**. While it is off nothing changes: the flat program, the corners, the warp and the picture are the same pixel for pixel (checked in the output self test). While it is on, the slice is drawn from a virtual projector onto the surfaces; its corners and warp are not used, while its mask, edge blending and colour still are. The block is saved as `spatial` inside the output mapping of a venue and only when it differs from the default, so every existing venue file is read and written exactly as before.
2. **A written coordinate system.** Right-handed, +X right, +Y up, +Z towards the audience, metres, angles in degrees. A device (projector or viewer) looks along −Z when all angles are zero; positive yaw turns left, positive pitch looks up, positive roll lifts the right side. Output coordinates are x to the right and y down from 0 to 1. Matrices are column-major as OpenGL reads them. The text is stored as `kSpatialConvention`, and `deviceMatricesToJson` prints the view, projection and combined matrices of a device, so a result can be reproduced by hand or in another program.
3. **The model.** A projector (position, yaw, pitch, roll, vertical field of view or throw ratio, aspect, lens shift in x and y as a fraction of the picture, near and far plane), a viewer camera with the same fields, up to 16 surfaces and up to 32 calibration points. A surface is four corners in metres in the order top left, top right, bottom right, bottom left as seen from the front, a rectangle of the picture (UV, default the whole picture), 1 to 32 divisions and a flag for both sides. The front is the side the projector has to be on; the back is not drawn unless both sides is on. A wall and the five visible faces of a box can be added with one button. Coordinates are limited to ±1000 m, names to 40 bytes, and a surface that has no area is refused.
4. **Two picture sources.** *Picture on the surfaces* gives each surface its own rectangle of the picture. *Picture seen by a viewer* lets a virtual camera look at the picture and every surface shows what that viewer would see there, for forced perspective where the picture is right from one spot only.
5. **A second shader program, the flat one untouched.** The spatial slices use their own program and vertex format. The picture coordinates are interpolated with perspective correction (the `q` term of projective texture mapping); the edge blend, mask and colour are computed from the output position without perspective (`noperspective`), so they stay in output space as they do for flat slices. Surfaces are drawn with a depth test and the depth buffer is cleared for every spatial slice, so a pillar in front of a wall hides it. An output window without a depth buffer draws the surfaces in list order and says so. A spatial slice with no usable surface draws nothing.
6. **Meshes are built on the processor.** `buildSpatialMesh` cuts away the back faces, clips triangles at the near plane, drops degenerate triangles and counts what it did (`drawn`, `facing away`, `behind the projector`, `cut at the near plane`, `outside the picture`); the interface shows the counts. The same code answers `castProjectorRay` and `pointLitByProjector` for tests and for the calibration view. A memory estimate (`spatialMeshBytesEstimate`) joins the output budget and equals the measured memory for the test wall.
7. **Manual calibration.** For every known point the user enters where it is in space and moves a green cross on the output until the light lands on the real spot, with a test pattern and markers (a green cross where the point should land, an orange X where the current pose puts it, a yellow line between them; the markers are drawn on the output, are part of a capture and are not sent over NDI). With four or more points that do not lie on one line, **Solve** finds the projector pose with a damped least squares method (Levenberg–Marquardt) on the pixel errors, from the current pose and, if that does not reach the tolerance, from up to 78 other start poses (26 directions around the points at two, four and eight times their spread, each looking at the middle of the points). With **also solve the field of view** it needs six points. The result is reported as the average and the worst error in pixels at 1920 wide, per point too, and is applied only after **Apply to the projector**, with Undo. A fit that is worse than the tolerance is reported as not found and changes nothing. The same solver is used by the tests, so the result is reproducible from the saved venue.
8. **Hardware auto-calibration is a later phase and is not built.** It needs a camera, structured light and real tests; none of that was possible here, and the manual model is the data format such a phase would write into.
9. **Tests with a CPU model.** `nvj_spatial_tests` (1017 checks, no OpenGL) covers the conventions, the matrices, the surfaces and the limits, the JSON round trip and damaged or huge input, the mesh, culling, near clipping, ray casting against the mesh, the camera source, occlusion, two overlapping projectors and the calibration (recovery of a known pose with and without noise, determinism, the field of view, wild starting poses, planar point sets, too few and collinear points). `--output-selftest` renders in the real window and compares the pixels with the same model on grids of probe points: a filling wall, oblique and tilted walls, the camera source with a crop, a picture rectangle, flips, edge blending, occlusion, back faces, near clipping, switching between flat and spatial and back with the memory returning to its start value, and the markers (with the fake NDI library also that they are not in the frame that NDI sends).

## Alternatives considered
- **Extending the corner and warp model.** Rejected: a corner mesh cannot express a pillar and a wall in one view with correct depth and cannot be reproduced from a projector position.
- **One shader for flat and spatial slices.** Rejected: it would have risked the flat output, which has to stay identical; a second program costs nothing when it is unused.
- **Perspective-correct blending and masks.** Rejected: edge blend and masks are defined in output space in the flat model and in a projector's own picture, so they stay there.
- **A black-box optimiser or a closed form pose.** Rejected for this version: damped least squares on pixel errors needs no extra library, reports an error the user can read and is easy to test; a closed form (a direct linear transform) needs more points and gives no pixel error.
- **Using a camera for the calibration now.** Not possible without hardware; kept as a separate phase.

## Consequences
- A person can describe a room, put the projector where it really stands, and get a picture that lands on a wall, a pillar or a box with the right perspective, without working out corners by hand.
- Old venues, old settings and every flat slice are untouched. A venue that uses 3D mapping should be read by an older program with the block ignored, because the venue reader takes only the keys it knows; that slice would then show as an ordinary flat slice. This was not tried with an older build.
- A spatial slice costs a mesh (a few hundred bytes for a wall, more with divisions) and a depth buffer in the output window; a slice that is off costs nothing.
- The calibration is only as good as the measured points. The interface says so and shows the error per point.

## Validation / open questions
- **Run (Linux, Mesa llvmpipe, Xvfb, no graphics card):** `nvj_spatial_tests` 1017 checks, `--output-selftest` 553 checks (581 with the fake NDI library, 0 failed), the whole `ctest` suite, `scripts/check_i18n.py`, `scripts/check_test_matrix.py`, `scripts/check_release.py`, `scripts/build_manual_site.py --check`, and a look at the interface in screenshots.
- **Not done:** a real projector and a real room (the calibration was tested on points that a known pose produced, not on measured ones), two or more real projectors with an overlap, edge blending by eye, a real graphics card (depth precision, driver differences), Windows at run time, the calibration view with a mouse on a real display, and a review by someone else.
- **Open for the maintainer:** whether to build the camera-based auto-calibration as its own request once a camera and a projector are available; whether surfaces need more shapes than flat rectangles (a cylinder, a dome, a mesh file); whether the limits (16 surfaces, 32 points, 32 divisions) are right.
