# ADR 0037: GPU particles with transform feedback and a processor fallback

- **Status:** Accepted for the local part (requested by MarlonXDev as prompt 19), **off by default** until it has been tried on a real graphics card. Issue [#102](https://github.com/MarlonXDev/NyrexVJ/issues/102). Compute shaders, particle collisions, trails, sorting and textured or mesh particles are **not built** and stay Proposed.
- **Date:** 2026-11-25
- **Owners:** Maintainers (pending assignment)
- **Related:** [GENERATORS.md](../GENERATORS.md), [PERFORMANCE.md](../PERFORMANCE.md), [INTERFACES.md](../INTERFACES.md), [ADR 0036](0036-text-particles-chains.md), [ADR 0011](0011-render-pipeline-optimisation.md)

## Context
The particle clips of 0.43.0 simulate on the processor and are capped at 16,384 particles. A VJ asks for clouds of hundreds of thousands of points that follow the beat. The task asked to decide from the code between OpenGL 3.3 transform feedback with instancing, an optional compute backend (OpenGL 4.3) or a clearly delimited later upgrade, to keep the result deterministic and the graphics memory bounded, to keep a safe fallback, to avoid a global renderer rebuild and to measure 1080p and 4K.

## Findings (what existed before)
- **Existed:** the processor particle clips (`core/particles.*`, `render/generators.*`), one instanced draw call per place, 24 bytes per particle, 16,384 at most, `.nyxpart` version 1.
- **Existed:** the OpenGL context is requested as 3.3 core with forward compatibility (`src/main.cpp`). The generated loader (`third_party/glad`) contains every function; transform feedback is core in 3.0, so it is usable on a 3.3 context. `glDispatchCompute` is a function pointer that stays null on a 3.3 context.
- **Not found:** any simulation on the graphics card, any transform feedback or compute code.
- **Not verified:** which context version real drivers return for a 3.3 request. The build machine's Mesa returns 4.5 for it; Windows drivers often return the highest compatible version, macOS stops at 4.1 (no compute at all). Nothing here depends on it, and the code never assumes more than 3.3.

## Decision
1. **Transform feedback on the 3.3 context, not compute.** One state buffer pair (ping-pong, 8 floats per particle) lives on the card. One vertex-shader pass per fixed 1/60 s step reads the old buffer and writes the new one with rasteriser discard. One instanced draw reads the same buffer. Compute needs 4.3, would need a 4.3 context request or a second code path and would leave macOS out; for a one-pass particle update it gives nothing that transform feedback does not. A compute backend stays a possible later upgrade behind the same `GpuParticleSystem` interface and needs its own decision.
2. **A ring buffer instead of a free list.** Particles are born into consecutive slots of a ring; the oldest slot is reused when the ring wraps. The processor knows exactly which slots a step creates from the step counter, so nothing is read back from the card, nothing stalls and no atomic counter is needed. Slots that were never used are neither updated nor drawn. The price: when the pool is smaller than rate times lifetime, young particles replace old ones that are still alive (counted and shown as reused).
3. **Determinism by construction.** All randomness is a stateless integer hash of seed, birth number and stream number (PCG hash on `uint`, which GLSL 3.30 and C++ compute identically). The schedule (steps, how many are born, where) is computed on the processor by one class (`gpuparticles::Scheduler`) from the same clock, beat and level as the processor particles, at a fixed 1/60 s with at most 8 steps per frame. The same file, seed, clock and audio give the same state on the same computer, and the self test compares the card with a processor reference (`gpuparticles::Reference`, the same algorithm) and with itself bit for bit. **Not claimed:** identical bits across different graphics cards; `sin`, `cos` and fused multiply-add are allowed to differ in the last digits. The reference matched exactly on Mesa llvmpipe, which computes on the processor and says nothing about real cards.
4. **Bounded memory.** 64 bytes per particle (two buffers of 32). One setting, Graphics memory for GPU particles (8 to 512 MB, default 64), is a budget shared by all GPU clips; a pool is cut to what is left (in steps of 1,024) and refused with a message below 1,024 particles. A single pool is at most 1,048,576 particles (64 MB). A step creates at most 131,072 particles, a burst at most 100,000, the rate at most 200,000 a second. A clip can play in up to 16 places, each with its own pool, all inside the one budget. The budget is returned when a pool or a clip is released. The numbers are part of `gpuMemory().generators`.
5. **A safe fallback in every case.** The same file runs on the processor, through `particles::cpuEquivalent`, which scales the rate down so that rate times lifetime fits the processor limit, when: the setting is off (the default), the driver has no transform feedback, the shaders do not compile or link, the budget is used up, buffer creation fails, or the first frames raise an OpenGL error. The clip carries the reason, the window shows it, nothing else is affected and the show keeps running. A fault that goes away is picked up again when the clip or the setting changes. The library thumbnails always use the processor version.
6. **No renderer rebuild.** `GpuParticleSystem` is owned by a slot of the existing `ParticlePlayer`; the engine's draw path, the layer targets, blending and outputs are untouched. The new GL state is bound and unbound inside one function each and the self test checks that no program, vertex array, feedback buffer, discard or blend state is left behind.
7. **One file format.** A GPU clip is a normal `.nyxpart` version 1 file with optional keys (`backend`, `gpuCount`, `swirl`); the program of 0.43.0 ignores them and clamps the rate, so the file still opens there as a processor clip. Swirl works on the processor too (it is zero in every old file, so old files behave exactly as before). Three built-in GPU clips (GPU Nebula, GPU Beat Burst, GPU Rain) do not change the six processor presets.
8. **A self test in the real engine.** `--gpu-particle-selftest [FRAMES]` runs 30 checks against OpenGL (reference match, bit-exact repeat, seed and audio response, beat bursts, ring reuse, budget and release, fallbacks, state left clean, picture visible and repeatable, the engine switch) and, with FRAMES, a benchmark of 16,384 to 1,048,576 particles at 1920 x 1080 and 3840 x 2160. `nvj_gpuparticles_tests` (217 checks) tests the scheduler, the reference, the budget and the file format without a graphics card. Both run in CI.

## Alternatives considered
- **Compute shaders.** Needs a 4.3 context; macOS has none. Same result for this job. Later upgrade at most.
- **A free list with atomic counters or a readback of the alive count.** Compaction would keep young particles alive longer in a small pool, but needs 4.3 atomics or a card to processor readback every frame that stalls the pipeline. The ring is simpler and has no stall.
- **Raising the limit of the processor system.** Simulation and upload of a million particles a frame on the processor does not fit a frame.
- **On by default.** Not before a real card has run the self test and a show. The default stays off; the maintainer decides when to turn it on.
- **A global option to render everything on OpenGL 4.x.** A renderer rebuild without a need.

## Consequences
- Four new source files (`core/gpu_particles.*`, `render/gpu_particles.*`), a self test (`app/gpu_particle_selftest.*`), `tests/test_gpu_particles.cpp`, new start options `--gpu-particles`, `--generator-select` and `--gpu-particle-selftest`, and two settings (`gpuParticles`, `gpuParticleBudgetMb`).
- The cost of the update pass grows with the pool that is in use, not with the number alive: a million-slot pool costs a million vertices a step even when most are dead. The draw cost grows with the pool and with the fill rate (size times blending).
- `glGetError` is read only for the first three frames of a pool; later driver errors are not caught.
- No readback in normal use, so the window shows slots in use and reused, not the exact number alive.
- Float results can differ between graphics cards in the last digits, so a picture may differ slightly between two computers.

## Validation / open questions
- Done here, on Linux with the Mesa software renderer (OpenGL 4.5 core context): 217 checks of `nvj_gpuparticles_tests`, 30 checks of `--gpu-particle-selftest`, the whole suite (41 groups), the translation check, `--check-shaders`, the earlier `--generator-selftest`, and screenshots of the window in English and German.
- **Not done:** a real graphics card (all numbers in [GENERATORS.md](../GENERATORS.md) are a software renderer and only show how the cost grows), a 3.3-only driver, Windows beyond the CI build, a mouse and keyboard test of the new controls, a 4K composition (the program offers 960 x 540 to 2560 x 1440; 4K was measured on the generator alone), and a show.
- **Open for the maintainer:** when GPU particles may be on by default, the default budget of 64 MB, whether a compute backend is wanted, and whether trails or collisions should be taken on as a separate task.
