# ADR 0038: Graphics memory diagnostics, a memory budget with priority release and warnings

- **Status:** Accepted for the local part (requested by MarlonXDev as prompt 23), the budget is **off by default** and nothing is released or lowered while it is off. Issue [#104](https://github.com/MarlonXDev/NyrexVJ/issues/104). A DXGI or Vulkan memory query, a per clip quality level chosen by the user and a second profiler are **not built**.
- **Date:** 2026-11-25
- **Owners:** Maintainers (pending assignment)
- **Related:** [PERFORMANCE.md](../PERFORMANCE.md), [INTERFACES.md](../INTERFACES.md), [ADR 0010](0010-video-decode-pipeline.md), [ADR 0011](0011-render-pipeline-optimisation.md), [ADR 0037](0037-gpu-particles.md)

## Context
The Performance page already had a render pass profiler, a GPU timer, an idle release of images and videos, a frame rate limit, a render quality setting and an estimate of the graphics memory by group. What a show operator could not see was whether the driver was short of memory, how much picture data a video load pushed to the driver every second, how slow the worst frames were over a minute and how many frames were missed, and nothing kept the memory of a show with many clips inside a number the operator chose. The task asked to extend what exists, to keep measured values apart from estimates, to document the limits of the APIs, to release resources by priority and never one in use, to offer optional quality levels and to test with a VRChat like load on real hardware without promising speed.

## Findings (what existed before)
- **Existed:** `Engine::gpuMemory()` (an estimate per group, counted from what NyrexVJ allocates), the render pass profiler and GPU timer (`core/pass_profiler`, `Engine::gpuFrameMs`), `FrameStats` with average, 5 % worst and maximum, the frame rate limit, `fixedQualityScale` and Automatic quality, idle release of images after 120 s and of videos after 6 s, prewarming of the next video of a layer, a video cache size limit for converted files.
- **Existed, not enough:** no 99th percentile, no dropped frame count, no measured driver memory, no upload traffic, no budget, no priority, no warnings.
- **Not found:** any memory query of the graphics API. The program uses OpenGL 3.3 core; `GL_NVX_gpu_memory_info` and `GL_ATI_meminfo` are in the generated loader.
- **Not verified:** the numbers a real NVIDIA or AMD driver returns, because there is no graphics card here. Mesa's software renderer exposes both extensions and returns values that are sometimes meaningless (a `GLint` count of kilobytes that wrapped negative was seen on the build machine).

## Decision
1. **Measured and estimated stay separate in code and on screen.** `gpudiag::DriverMemory` holds what the driver says (source, total if reported, free, evicted bytes and count) and is `None` when the extension is missing or the values are not usable (a total of zero or less, a negative value). The estimate is what `gpuMemory()` counts. The page shows them in two blocks with their own headings and never adds or compares them; the budget is compared with the estimate only, because the driver number includes every other program.
2. **A pure module, a thin engine.** `core/gpu_diag.*` (in `nvj_core`, no OpenGL) holds the driver readout interpretation, the sliding window percentiles, the frame watch, the traffic meter, the warning rules with hysteresis, the eviction planner and the pressure ladder, tested by `nvj_gpudiag_tests` (363 checks). `Engine` only feeds it numbers and carries out the plan.
3. **Percentiles from a window, not from 240 frames.** `WindowStats` keeps 60 one second slots with a histogram of 0.25 ms buckets up to 64 ms plus an overflow bucket; P95 and P99 are read from the histogram (rounded up to a bucket edge, never above the window maximum) and are shown only after 120 samples. Frames of two seconds or more are stalls (a loaded dialog, a suspended computer) and are not counted as frames.
4. **Dropped frames are an estimate from the time between frames.** A frame is late when it takes more than 1.5 times the budget; the frames it missed are `max(1, round(interval / budget) - 1)`. This is counted from the program's own frame times, not from the display's present statistics, which OpenGL does not give.
5. **Upload traffic counts continuous picture data.** `VideoUploader::present` adds the tight source bytes (the bytes handed to the driver, without row padding) of every video and live source frame to one atomic counter; the engine turns it into bytes per second, the highest second of the last ten and the total. Images and 3D models are loaded once and are not counted. This is the traffic NyrexVJ causes, not the bus load the driver reports.
6. **Warnings with thresholds the user can change.** Eight rules (slow frames from the 99th percentile, dropped frames per minute, memory near and over the budget, resident memory over the budget, little free driver memory, driver evictions, very high upload) raise after 2 s and clear after 6 s so a warning does not flicker. Thresholds are settings (`diagP99Percent` 150, `diagDroppedPerMinute` 5, `diagMemoryPercent` 85); the status bar shows the count in the colour of the worst one and its tooltip names them. Warnings never change what plays.
7. **A budget that is off unless set.** `gpuMemoryBudgetMb` is 0 (off) or 256 to 65,536. With 0 the engine behaves exactly as before: no eager loading change, no release, no quality cap. The budget is compared with the estimate every 0.25 s.
8. **Priority release, never of something in use.** Over the budget, resources that are loaded, not in use and idle for at least 5 s (1 s once the pressure is at step 2) are released in the order prepared videos, images, 3D scenes, and inside a class the longest idle and the biggest first, until the estimate is at 85 % of the budget, at most 8 per pass and only those of 1 MiB or more (releasing a 40 KiB model costs a reload and frees nothing). A cell that is playing on any layer is never released, and in this mode only the playing and the next cell of a layer (and images whose thumbnail is still to be drawn) are loaded, so the idle time of the rest is real. A released image loads again when it is launched.
9. **A pressure ladder and optional quality levels.** When the estimate stays over the budget for 3 s the program steps up (stop preparing the next clips, release after 1 s, layers at 75 %, layers at 50 %), and steps down again after 12 s below 75 %. The two resolution steps need the extra setting `gpuMemoryLowerQuality` (off by default); they use the existing layer scale and never touch master effects or outputs. While a step is raised, idle images are also released down to 70 % of the budget so that the ladder can come back down.
10. **Settings, not new profilers.** Everything is added to the Performance page next to the existing Memory block and the existing Measured table (which gains a column for the slowest 1 %). There is no second profiler window.
11. **A self test in the real engine.** `--gpu-diag-selftest [FRAMES]` imports eight large images, loads them all with the budget off, turns the budget on and checks the release, that the playing and the next image stay, that a released image loads again, that turning the budget off restores the old behaviour, the pressure ladder with four playing layers (step 4, half resolution, playing images kept, warning logic), the recovery, the upload counter against a known number of bytes and the driver readout, and removes its files again. It runs in CI.

## Alternatives considered
- **A DXGI (`IDXGIAdapter3::QueryVideoMemoryInfo`) or Vulkan (`VK_EXT_memory_budget`) query for Windows.** It reports the budget the operating system gives this process and would be the most reliable number on Windows, but it cannot be built or run here, and a function that was never run is not shipped as a measurement. Proposed as a follow up that a maintainer with a Windows machine can verify.
- **Trusting the estimate as the card's memory.** It counts what NyrexVJ allocated; textures can use more in the driver, and other programs are invisible. Shown as an estimate, named as one, and used only for the budget.
- **Releasing active clips under pressure.** Would cause a black picture in a live show. Never.
- **Lowering the resolution first.** A visible quality loss. It is the last step and optional.
- **Counting upload traffic with a GPU query.** OpenGL has no counter for it; counting what is handed to the driver is exact and cheap.
- **Percentiles from the last 240 frames.** Four seconds at 60 FPS say nothing about the minute.
- **On by default.** The budget needs a number only the operator knows; the default stays off.

## Consequences
- New files `core/gpu_diag.*`, `app/ui_diagnostics.cpp`, `app/gpu_diag_selftest.*`, `tests/test_gpu_diag.cpp`; new start option `--gpu-diag-selftest`; seven new settings (`gpuMemoryBudgetMb`, `gpuMemoryTrim`, `gpuMemoryLowerQuality`, `diagWarnings`, `diagP99Percent`, `diagDroppedPerMinute`, `diagMemoryPercent`).
- With a budget set, images that were not used for a few seconds are unloaded, so launching one after that can show a short gap while it decodes and uploads; it was 7 frames (290 ms) for an image of 3584 x 3584 pixels on the software renderer of the build machine and is not a number for a graphics card.
- Evicted videos are re-prepared by the existing next clip logic only while the pressure is below step 1.
- The driver block is empty on drivers without the extensions and on software renderers with unusable values.
- A budget below what the playing clips need cannot be met: the warning says that what cannot be released is over the budget, and the quality steps are the only relief.

## Validation / open questions
- Done here, on Linux with the Mesa software renderer (OpenGL 4.5 core context): `nvj_gpudiag_tests` (363 checks), `--gpu-diag-selftest` (15 checks, 20 s), the whole suite, the translation check (2327 keys), screenshots of the page.
- **Not done:** a real graphics card (the driver readout was only seen from Mesa), Windows beyond the CI build, a VRChat like load with a second GPU program running (manual tests M-GD-1 to M-GD-3), a mouse and keyboard test of every control, a measurement of the cost of the diagnostics per frame on a real machine (the per frame work is one counter read, one histogram increment and, every 0.25 s, a pass over the media and scene lists).
- **Open for the maintainer:** a default budget, whether a DXGI or Vulkan query should be added for Windows, whether the quality steps should be on by default, and the warning thresholds after real shows.
