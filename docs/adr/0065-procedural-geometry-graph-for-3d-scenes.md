# ADR 0065: A procedural geometry graph for 3D scenes

- **Status:** Accepted for the geometry graph, its nodes, its limits, its cache, instancing through shared meshes, music through the shader, the scene document version 5 and the switch, requested by MarlonXDev (2026-11-27 20:32, prompt 32): a separate, optional node graph that creates and changes 3D geometry (primitives, transforms, noise and deformation, instances, materials, audio and beat control), without reusing the 2D node editor, with limits, a cache, versioned files, visible errors and a benchmark, and without changing a live show that does not use it. True GL instancing, a node canvas with draggable boxes and the choice of the default of the switch are **open questions** (below).
- **Date:** 2026-11-28
- **Owners:** Maintainers (pending assignment)
- **Related:** [SCENE3D.md](../SCENE3D.md), [INTERFACES.md](../INTERFACES.md), [PERFORMANCE.md](../PERFORMANCE.md), [TESTING.md](../TESTING.md), [ADR 0004](0004-scene-document-and-clip-pack.md) (the scene document and the clip pack), [ADR 0006](0006-clip-creator.md) (the editor), [ADR 0025](0025-3d-engine-2.md) (model import and its limits), [ADR 0062](0062-audio-reactive-3d-materials-sources-and-targets-for-scene-bindings.md) (music on materials, the Inflate and Ripple targets), [ADR 0064](0064-shared-3d-scene-hierarchy-model-reuse-and-shared-worlds-across-layers.md) (the hierarchy, model reuse and the culling that instances use)

## Context
- State at main `90a27a9` (0.70.0), as an inventory:
  - **VORHANDEN:** eight built-in primitives (`primitiveMesh` in `src/scene3d/primitives.cpp`) with a transform, a material, animations and music rows per object (`src/scene3d/scene_doc.cpp`, `src/scene3d/doc_build.cpp`); a repeat of an object as a Ring or a Line (`RepeatKind` in `src/scene3d/scene_model.hpp`, built in `doc_build.cpp`); music on the whole object and in the vertex shader (Scale, Emissive, Twist, Lift, Hue, Roughness, Texture shift, Inflate, Ripple, `src/render/scene_player.cpp`); frustum culling of instances and model reuse (0.70.0); the loader thread of `ScenePlayer` that builds a scene document off the render thread; limits for a scene (`GltfLimits`, `kSceneMaxInstances` of 8,192); the scene document, the clip pack and a Clip Creator with a live preview; imported models (`src/scene3d/gltf.cpp`, its own limits); a 2D node editor for effects.
  - **TEILWEISE:** shapes could only be varied with the eight primitives and with deformations in the shader. The deformations move vertices on the graphics card and do not change the mesh, so they cannot roughen a surface, join two shapes or make a ring of rocks that differ from each other. The repeat copies an object in a Ring or a Line with no variation.
  - **NICHT GEFUNDEN:** any way to build or change a mesh from nodes, noise on the geometry, subdivision, merging of shapes, Grid and Scatter layouts with a seed, a size variation per copy, a cache for generated geometry, limits for generated geometry, and any way to see why a generated shape failed.
  - **NICHT VERIFIZIERT:** the frame time on a real graphics card, with many instances, and next to VRChat; the editor used by hand.
- Not part of this change, by the wording of the request: the 2D node editor (a graph of its own is built), model import (it keeps its path), and GPU particles (a different feature with its own prompt).

## Decision
1. **A graph of its own, in the scene document.** A document has up to 8 graphs (`graphs`), each with a name and up to 48 nodes. An object of the new kind `graph` names one of them. The node types are Primitive, Subdivide, Transform, Noise, Twist, Merge, Instance, Material, Audio and Output (one only). Each node has up to two inputs that name other nodes, so the graph is a directed graph that is evaluated from the Output backwards. A loop is an error that names the node, and the editor offers only inputs that would not make a loop.
2. **Evaluated once, on the processor, off the render thread, and cached.** The evaluation runs in the loader thread of the scene (the same place where a scene document is built), never per frame. The result is cached by a hash of the content of the graph (8 graphs and at most 600,000 vertices, least recently used out), so showing a scene again, a second layer with the same clip or two objects with the same graph does not build it again. Objects that use the same graph share one mesh in the scene when the graph has a Material node; without one every object gets its own material and so its own mesh.
3. **Limits.** 48 nodes, 200,000 vertices, 1,000,000 indices, 1,024 instances, 4 subdivision levels, 4 octaves, 8 graphs, and **4,000,000 triangles drawn per frame by one graph** (the triangles of the mesh times the number of instances, because every instance is a draw call). The last one was added late, when I went through the limits again: 1,024 instances of a sphere subdivided three times (196,608 triangles) would have asked for 201 million triangles per frame and no other limit stopped it. A graph that reaches a limit fails with a message that names the node (`Too many vertices at node: n5, 210000 > 200000`); the object is left out and the scene plays.
4. **Instances are nodes that share one mesh.** An Instance node gives the wrapper object one child node per instance, all pointing at the same mesh. The geometry is stored and uploaded once (114,480 bytes for 1, 10 or 1,000 instances of the sphere), the culling of 0.70.0 applies to every instance, and music reactions of the wrapper are inherited by the children. This is **not GL instancing**: each instance is a draw call. Instancing with one draw call needs a second draw path in the scene renderer (per-instance matrices as vertex attributes, and a way to combine it with skins, culling and the shader targets) and was not built; see the open questions.
5. **Music goes through the shader.** An Audio node writes a music row (a source, a target and an amount) onto the wrapper object, with the rule of ADR 0062. The targets that can be chosen are the ones that act in the shader or on the object (Scale, Emissive, Twist, Lift, Hue, Roughness, Texture shift X and Y, Inflate, Ripple); a target that would need a new mesh is not on the list. So **music never runs the graph again**: with the music on, the cache has no new miss (6 and 6 in the test).
6. **Errors are visible and never stop the clip.** A failed graph is named in the warnings under the Clip Creator preview and in the log (`The geometry graph has errors, object skipped: Graph object (Rock)`, then the lines of the graph, for example `Loop through node: n3`), the object is left out and the rest of the scene is drawn. The messages are built as a fixed English start plus the node, so they can be translated (a test checks that each kind of message has a translation in all seven languages).
7. **Files.** A document is written as `"version": 5` only when it has a graph or an object of the kind `graph`; otherwise it stays version 1 to 4 and is the old file byte for byte. Version 5 is refused by 0.70.0 and older with their message about a newer version, and version 6 is refused by this program. A graph is repaired on load (ids, limits, unknown node types, an audio source or target that is not known), and each repair is named in the warnings.
8. **The switch.** Settings, Performance, **Geometry graphs**, on at the start, written to `settings.json` only when off. It is read when a scene is loaded: off leaves graph objects out and says so in the warnings. A document without a graph does not depend on it.
9. **The editor.** The Clip Creator has Add object, Geometry graph, a Graph drop-down, New, Duplicate and Delete graph, a name, and a list-based graph editor (a row per node with its inputs and values, Add node, Remove node, and a line with vertices, triangles, instances and the time of the last evaluation). It is not the 2D node editor and has no canvas.
10. **A demo.** `docs/examples/geometry-graph/Rock Garden.nyxclip`: a ring of 14 rocks that grows with the kick and a twisted torus knot that swells with the bass. `nvj_geometry_tests --write-demo <folder>` writes it, and a test checks that the file in the repository is the one the code writes.

## Alternatives considered
- **Reusing the 2D node editor.** Rejected, because the request says not to: its data model (a chain of effects on a picture), its canvas and its evaluation are made for textures and not for meshes.
- **Evaluating the graph on every frame.** Rejected: music would run the whole graph 60 times a second. Music is limited to targets that act in the shader.
- **True GL instancing for the Instance node.** Not built now. The saving is draw calls, not memory (the mesh is already shared), and it needs a second path through the renderer that also has to respect the culling, skins and the targets of 0.68.0. The measurement below shows where the cost goes, and the decision is left to the maintainer.
- **Generating the geometry on the graphics card (transform feedback or compute).** Rejected: the target is OpenGL 3.3 without compute shaders, and a result on the processor can be counted, limited and cached.
- **Storing the generated mesh in the document.** Rejected: the document would grow by the size of the mesh and the graph could no longer be edited. The graph is the source and the mesh is a cache.
- **A node for every shape feature, with attributes per vertex.** Rejected for now. Ten nodes cover the list in the request; a larger system can be added when a concrete need appears.

## Measured
All values come from `nvj_geometry_tests`, `NyrexVJ --scene-selftest tests/data/models` (a real OpenGL context on Mesa llvmpipe, a software rasteriser on two processor cores, one machine, **not a graphics card**) and the full `ctest`. The frame times are for a 256 x 256 picture, best of three rounds of 60 frames. Run to run they spread widely on this shared machine (for example 201 to 333 ms for 1,000 instances), so the figures are ranges of four runs and not an exact value.
- **Unit tests:** `nvj_geometry_tests` is new, 496 checks, 0 failed: every node and its limits, loops and missing inputs, the vertex, index, node, instance, graph and triangle limits, determinism, the cache, JSON and documents with damaged and extreme input (a fuzz run), scene version 5 and the refusal of 6, the scene build, the setting, a clip pack round trip, the translations of all messages in seven languages and the demo file. `nvj_world_tests` (840 checks) and `nvj_creator_tests` were adjusted for the new kind and the version.
- **Render tests:** the scene self test has 10 new checks and passes 112 of 112. A graph with one sphere draws the same picture as the sphere object (46,834 lit pixels each, same hash). The default rock draws, differs from the sphere and draws the same twice. 1, 10 and 1,000 instances share one mesh (1 mesh, 114,480 bytes each) and every instance is drawn or culled (1, 10 and 1,000 drawn, none culled in this view). Music changes the picture of a graph with Audio nodes (4,042 to 8,280 lit pixels) and does not change the picture of the same graph without them, and the cache has no new miss (6 and 6). A bass reaction deforms the mesh in the shader (27,111 to 42,841). With the switch off the object is left out and the picture is the same as for a scene that never had it. A graph with a loop is reported and the rest of the scene draws.
- **Same picture as 0.70.0:** the hashes of the 7 built-in scenes, the 7 camera cases and the music-material preview of a 0.70.0 build and of this one are the same.
- **CPU (the loader thread):** the default rock (a sphere subdivided twice, with noise; 24,897 vertices, 147,456 indices) takes 10 to 16 ms to evaluate in two benchmark runs and 0.016 ms when it comes from the cache. The largest graph of the benchmark (98,945 vertices with noise) takes 50 to 80 ms; one level more is refused by the vertex limit after 10 to 16 ms. Building a scene document with a sphere graph and 1, 10 or 1,000 instances takes 0.26 to 0.58 ms the first time (the evaluation of the graph included) and 0.04 to 0.31 ms again. The hash that decides a cache hit takes 0.015 ms. The render thread does none of this.
- **Graphics memory:** 114,480 bytes for a sphere graph with 1, 10 or 1,000 instances (the same mesh), 1,784,880 bytes (1.7 MiB) for the rock; no test comes near the scene limits. The upload takes 0.05 to 0.24 ms for the instance scenes and 0.61 to 0.95 ms for the rock, on the render thread at the first draw.
- **Frame time (software OpenGL, 256 x 256, four runs):** 1 instance 1.71 to 1.79 ms, 10 instances 2.37 to 2.91 ms, 1,000 instances 201 to 333 ms; the rock 5.3 to 9.0 ms against 1.7 to 2.3 ms for a sphere; 64 instances 14.5 to 20.1 ms for the graph against 14.3 to 21.2 ms for the existing repeat with 64 copies, so a graph costs what the repeat cost. With music rows the numbers are inside the same ranges for 10 and 1,000 instances (2.00 to 2.43 and 200 to 320 ms), so the rows add no cost that can be seen in the noise. The pair for 1 instance (1.7 ms without and 0.4 ms with music) repeats in every run and is not an effect of the music rows themselves; the music changes the size of the object on the screen and a software rasteriser pays by the pixels. It was not looked into further. **The cost of 1,000 instances is 0.2 to 0.3 ms each here, which is the rasterising of 3,072 triangles per sphere on the processor; on a graphics card this is expected to be much lower, but that is not measured.**
- **Mutation probes (a fault put in, then reverted):** 14 faults. Unit tests: the loop check of the editor, the vertex limit, the cache hash, the jitter, the mirror, the normals under uneven scale, the instance limit, the graph limit of a document, the version written for a document without graphs, the triangle budget and the German translation of its message (11); renderer: the switch ignored, the music rows of a graph dropped and the instances all placed at the origin (3). Twelve were caught at once, each by a check that names the fault. **Two were not**: the vertex limit and the normals under uneven scale had no test of their own. One more check was weaker than its name: "music changes the picture" also passed with the music rows dropped, because the default scene reacts to music on its own (another check caught the fault). Tests were added or sharpened (every vertex normal of an unevenly scaled sphere against the analytic normal, the vertex limit on a Primitive and on a Merge, and a comparison with the same graph without Audio nodes under the same music), and all three faults are now caught. One check of my own was wrong (it assumed that the scene without the graph object is darker; the scene is framed again and the cube fills the picture) and now compares the pixels with a scene that never had the graph.
- **Full `ctest`:** 71 of 71 programs pass; the local copy of the CI script (all steps, including the scene variants and the two-instance tests) ends with `fail=0`.
- **By hand:** nothing in the interface was clicked through for this release (see below).

## Not done
- **GL instancing.** One draw call per instance remains. Whether it pays depends on the real card.
- **A node canvas.** The graph editor is a list; there are no boxes to drag and no preview of a single node.
- **Per-vertex attributes, vertex colours, UVs from nodes, curves, booleans and a node for an imported model.** The nodes keep the UVs of the primitive and make none of their own.
- **Normals of a mesh that is deformed in the shader** (the limit of ADR 0062 stays).
- **Hot reload of one node.** A change in the editor evaluates the graph again (10 to 80 ms in the benchmark, in the editor's loader thread) and does not patch the mesh.
- **A real graphics card, Windows at run time (built in CI only), a long show, the frame time next to VRChat, a graph with 1,000 instances at 1920 x 1080, and the editor clicked through by hand (every row, the pickers, Add and Remove node, undo of the object fields, a graph of 48 nodes).** See `M-GEO-1`.

## Open questions for the maintainer
- **Should the switch be on at the start?** Now it is on, because a document without a graph does not depend on it and a document with one should play. The other choice is off until the first graph is made.
- **GL instancing?** The numbers above are software-rasteriser numbers; a run of `--scene-selftest` on the target PC (and `M-GEO-1`) shows whether 1,000 instances of a 3,072-triangle shape are a problem there. If they are, lower-polygon primitives and a lower triangle budget are the cheap answer, GL instancing the real one.
- **The budget of 4,000,000 triangles drawn per graph.** It is a guess that keeps a graph from asking for hundreds of millions; the scene as a whole is not budgeted, so several graphs can add up. A budget per scene needs a decision about what a show may spend.
- **A canvas editor?** The list editor works and is translated; whether it is good enough for the way you work is something only a session with it can tell.
- **Two objects with the same graph.** They share the mesh. A per-object seed would break the sharing; it is not offered.

## Consequences
- `SceneDoc` has `graphs`, `DocObject` has `graph`, `PrimitiveKind` has the kind `Graph`, `Settings` has one new field and `settings.json` one optional key (`sceneGeometryGraphs`); older programs ignore the key.
- No control id is added and the network sync does not change: a graph lives in the scene document, and the music rows are the ones that already exist.
- The cache holds at most 600,000 vertices of geometry on the processor, the graphics memory of a graph is the same as the one of the mesh it makes, and nothing is allocated for a document without graphs.
- A document without graphs is written exactly as before. One with graphs is version 5 and 0.70.0 and older refuse it with the existing message.
- A scene with graphs loads slower by the evaluation time (up to 80 ms for the largest benchmark graph, once, in the loader thread) and not by anything per frame.
- Not run on a real graphics card or on Windows beyond the CI build; see `M-GEO-1`.
