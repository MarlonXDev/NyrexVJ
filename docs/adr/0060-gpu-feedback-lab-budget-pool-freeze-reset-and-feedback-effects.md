# ADR 0060: GPU feedback lab: a budget, reuse, freeze and reset for feedback buffers, and four effects that do not depend on the frame rate

- **Status:** Accepted for the budget, the pool, Freeze and Reset, the frame time as `uDelta` and the four new effects, requested by MarlonXDev (2026-11-27 20:32, prompt 38): make the feedback pictures safe and controllable (memory, resolution changes, reset, freeze, no leaks) without a second render engine and without changing the effects that already exist. Whether Trails and Hue Feedback should get the same treatment is an **open question for the maintainer** (see below). Issue [#150](https://github.com/MarlonXDev/NyrexVJ/issues/150).
- **Date:** 2026-11-27
- **Owners:** Maintainers (pending assignment)
- **Related:** [PERFORMANCE.md](../PERFORMANCE.md), [SHADERS.md](../SHADERS.md), [INTERFACES.md](../INTERFACES.md), [TESTING.md](../TESTING.md), [ADR 0029](0029-rest-api.md) (the web interface lists the control ids), [ADR 0041](0041-multi-pc-sync.md) (network sync schema), [ADR 0045](0045-graphics-memory-diagnostics-and-warnings.md) (the memory estimate and its budget)

## Context
- State at main `7573ce1` (0.65.0): an effect that reads the previous picture (`usesPrevious`, `uPrev`) gets the last output of its own slot. The engine keeps those pictures in `feedback_` (two deck sets of five chains with four slots each, RGBA8), `previewFeedback_` and `chainPreviewFeedback_`. A buffer is made in `Engine::runChain` the first time an effect needs it, made again when the size does not match, released at the end of the frame when no effect used it, the other set is released when the deck changes, and everything is destroyed when the resolution changes or a composition is applied. There was no limit on how much memory they could take (one picture per feedback effect, 33.2 MB at 4K, up to 20 per deck set), no reuse of a released buffer (every switch of an effect off and on asked the driver for new memory), no way to hold or clear them from outside, and no way to see them in the memory overview (they were part of the render target sum).
- The buffers of shader plans (clips, filters, ISF) are another thing: RGBA16F, kept in `ShaderPassState`, budgeted since 0.29.0 (512 MB, `fitShaderScale`). They stay as they are.
- Trails and Hue Feedback multiply the previous picture by a number that is the same in every frame, so the length of a trail depends on the frame rate (at the top of Trails, `0.985` per frame is 0.40 per second at 60 frames and 0.11 per second at 144). They write 8 bit colour, so a slow fade stops where the step per frame is smaller than half a colour step.
- The node editor already refuses a connection that would make a loop, the compiler reports `loop`, and the loader refuses a file with a loop. A feedback node (`Previous`) is not a loop in that sense: it reads the buffer of the last frame.

## Decision
1. **Extend the existing path, do not add an engine.** The buffers stay where they were, in the same arrays, written by the same `runChain`. A new type `FeedbackTarget` (a render target that remembers the size of the picture it stands for) replaces the plain target in those arrays, so a buffer that runs smaller than the picture is not made again every frame.
2. **A budget.** `Settings::feedbackBudgetMb` (default 256, 0 = no limit, otherwise 64 to 8192) is the most the live feedback buffers may use together. `Engine::acquireFeedback` asks `fitShaderScale` (the function the shader buffers already use) for the largest of 1, 0.75, 0.5, 0.35 and 0.25 of the picture that fits in what is left. A buffer that fits only smaller is made smaller and sampled with normalised coordinates, so the effect looks softer but works. It is filled by taking every n-th pixel of the effect output (a nearest blit), not by a smooth reduction: the smooth reduction rounds to the nearest colour step and left a grey of 42 of 255 standing for ever (measured, see below); if not even a quarter fits, the buffer is **refused**, the effect runs with a black `uPrev` (it shows the live picture without trails) and the refusal is counted and shown. The first reduction and the first refusal are written to the log once. Changing the budget clears the feedback pictures once, because buffers that no longer fit are made again.
3. **A pool.** A released buffer is kept in a pool (at most 8) and used again for the next request of the same size; a buffer taken from the pool is cleared first, so nothing of the old picture shows. A buffer that waits for more than 300 frames (5 seconds at 60) is destroyed. The pool counts in the memory overview and is trimmed first when a new buffer would not fit in the budget. `Settings::feedbackReuse` (default true) turns it off; with it off the pool is emptied at once and the engine behaves as before.
4. **Freeze.** `Engine::setFeedbackFrozen(true)` skips the copy of the output of an effect into its feedback buffer. The effect goes on drawing the live picture over the held one. It is not saved with the show or the settings. Freeze does not apply to the buffers of shader plans.
5. **Reset.** `Engine::resetFeedback()` clears every feedback buffer and calls `ShaderPassState::clear()` for every shader state and the playground. It acts in the frame it is called in.
6. **Controls.** Two new control ids at the end of the list, `master/feedback-freeze` (toggle) and `master/feedback-reset` (trigger), so MIDI, OSC, the web interface and the Unreal link get them without any new code. The effect rack shows Freeze and Reset when the chain has a feedback effect, and Settings, Performance has the budget, the reuse switch, the number of buffers and the memory. **This changes the schema hash of the network sync**: two PCs on different sides of this release only exchange the clock until both are updated.
7. **`uDelta`.** The header every effect gets has a new `uniform float uDelta` (the time between two frames in seconds, 0 while the show is paused, at most 0.1) and three helpers: `fbKeep(halfLife)` (`exp2(-uDelta / halfLife)`), `fbFetch(q)` (the old picture, black outside the unit square) and `fbRound(c)` (rounds 8 bit colour at random, so a slow fade reaches black instead of stopping a few steps above it; the random value comes from an integer hash (PCG) of the pixel and of the bits of `uTime`, the same value for the three channels so a grey does not turn into coloured speckle). The old `hash21` was too weak for this: with it the half size buffer lagged far behind the half-life (22 against 13 at four seconds). Effects that do not use them compile to the same code as before.
8. **Four new effects**, appended after Prism Glass so no existing index moves: **Time Echo** (a fading copy, optionally pushed away and blurred), **Motion Smear** (a slow low pass of the picture over time, with a slide), **Feedback Transform** (zoom, rotation and drift of the old picture, the kick adds a small zoom) and **Accumulate** (average, lighten or a screen blend exposure, with gain and a kick flush). They all take their decay as a half-life in seconds, so they look the same at 30, 60 and 144 frames per second and hold still while paused.
9. **Trails and Hue Feedback are not touched.** The text of their shader bodies is guarded by a test (FNV-1a hashes `0x9d978c4ea30029a0` and `0x1be913d0574a9380`).
10. **Settings and files.** The two new settings are written only when they differ from the default, so a settings file that never changed them is written byte for byte as before (the frozen fixture of `nvj_compat_tests` did not change).

## Measured
All values come from `nvj_feedback_tests` and `NyrexVJ --shader-selftest` on Linux with Mesa llvmpipe (software OpenGL, one machine, not a graphics card). Frame times are wall clock per frame at 1280 x 720 and include the CPU rasterisation; the three runs I made differ by up to 3 ms for one layer and up to 6 ms for four layers, so smaller differences are noise. The memory values are exact byte counts.
- Unit tests: 3,740 checks, 0 failed. `ctest` 66 of 66, `--interface-uitest` 116 of 116, `--check-shaders` exit 0.
- Render tests: 48 new checks in `--shader-selftest`, all passed (190 of 190 in total).
  - **The half-life is real time.** A Time Echo set to one second takes a grey of 204 to 99, 102 and 99 after one second at 60, 30 and 120 frames per second (102 is the ideal). It holds 199 through three paused seconds and is at 103 one second after resuming. A neutral Feedback Transform holds 204 on a steady picture and is at 98 one second after the picture goes black. Accumulate halves in one second in the average mode (104) and the lighten mode (109), and in the exposure mode a steady 204 builds up to 254. Motion Smear with a half-life of 0.59 s is at 12 three frames after a cut (12 expected), at 144 after one second (141) and at 204 after ten seconds. Freeze holds 144 for three seconds and the picture fades again after Unfreeze (75 one second later, 72 ideal); Reset clears to 0 in the next frame, also for a shader buffer (255 back to 25 after one frame of a running accumulation).
  - **Trails stops above black.** With its Feedback slider at the top, 15 seconds after the picture went black, Trails still shows (33, 33, 33) on every pixel (the step of 0.015 per frame is less than half a colour step below 33), while Time Echo has 0 % of the picture lit after the same time. At the default slider (0.7) the fixed point is 1 of 255 and not visible.
  - **Budget.** Four layers with Trails at 960 x 540 use 8,294,400 bytes without a limit; with a 5 MB budget they use 5,184,000 bytes (two buffers smaller than the picture, none refused). A budget of 600 KB gives one buffer of 518,400 bytes instead of 2,073,600, and the echo is at 105 after one second (102 ideal). After 15 seconds that half size buffer shows 0 in the centre and has 8 % of the picture one step above black, where the full size buffer has 0 %: **a smaller buffer fades more slowly in the last steps**. A budget of 100 KB refuses the buffer (30 refusals counted, the live picture is shown, no echo, 0 bytes). Turning the budget off gives the full size back.
  - **Resolution changes.** Eight changes between 960 x 540, 1280 x 720, 1920 x 1080 and 2560 x 1440 with four buffers each: the byte count is exactly four pictures every time, no GL error, a lit picture. With the balanced layer resolution the buffers follow the layer size and return to full size.
  - **Reuse.** Twenty off and on switches of one effect make 0 new buffers and reuse 20 (with reuse off: 20 made, 0 reused). A released buffer waits in the pool and is gone after 320 frames. Six deck switches leave no more than four pictures of memory.
  - **Soak.** 1,200 frames with a random change every 40 frames (resolution, freeze, reset, an effect on or off, a parameter, a deck, the quality, the budget, reuse): peak 12,432,384 bytes of feedback memory against a ceiling of 66,355,200, 0 GL errors, no black sample, and after every effect was switched off 0 live buffers, 0 pooled and 0 bytes.
- Frame time (1280 x 720, one layer, final run): no effect 14.4 ms, Trails 23.5, Time Echo 31.5, Motion Smear 26.8, Feedback Transform 26.3, Accumulate 25.8, a frozen Time Echo 30.8; four layers without an effect 43.0 ms and with a Time Echo on each 110.4 ms. The first frame of an effect (the buffer is made) is within 5 ms of its later frames, except Time Echo on four layers (122.6 ms against 110.4 ms). One feedback picture at 1280 x 720 is 3,686,400 bytes.
- Freeze does not make the frame cheaper (30.8 ms frozen against 31.5 ms running): the effect still reads the old picture, only the copy is skipped.

## Not done
- **Trails and Hue Feedback** (below).
- Freeze for the buffers of shader clips and filters (Reset clears them, Freeze does not hold them).
- A smooth reduction of a smaller buffer. It would need a pass that rounds at random; the nearest copy is what keeps the fade honest, at the price of a rougher, more aliased trail while a buffer runs at half or a quarter of the picture.
- Feedback pictures with more than 8 bit (a 16 bit float buffer would double the memory; the stochastic rounding of the new effects is the cheaper answer).
- A budget per layer or per effect, a budget in milliseconds, and a warning in the status bar for a refused buffer (the Performance page shows it).
- A change of the frame-rate dependence of the shaders of other kinds. A shader file that wants the time between frames already has `iTimeDelta`.
- A real graphics card, Windows at run time (built in CI only), two PCs with the network sync (the schema change is unit tested through the control list, not between two programs), a run of hours, MIDI and OSC hardware for Freeze and Reset (the targets are tested through the router), and a look next to the old effects on a real output; see `M-FBK-1`.

## Open question for the maintainer: Trails and Hue Feedback
Trails and Hue Feedback decay by a number per frame and write plain 8 bit colour. The measurement above shows two consequences: at the top of the Feedback slider Trails never gets below a grey of 33 of 255, and a trail is about four times shorter at 144 frames per second than at 60. The proposal is small: rewrite their shaders with `fbKeep`, `fbFetch` and `fbRound` and keep the sliders as they are. The cost is that every preset that uses them looks different (shorter trails at high frame rates, black at last instead of a grey), and the guarded bodies of the two shaders would change. Two ways, say which one:
- **Change them** (one release, a changelog line), or
- **Keep them and add two new effects** with the exact behaviour (for example *Trails (exact)*), so no preset changes. This is cheaper to undo.
Nothing was changed, because it changes the look of shows people have already built.

## Consequences
- `Settings` has two new fields and `settings.json` two optional keys; older programs ignore them.
- The control list has two more ids at its end. A show saved on 0.66.0 with a MIDI mapping or a timeline lane on these ids loads on an older program with those entries dropped. The schema hash of the network sync changes (see 6).
- `GpuMemory` has a new member `feedback` that is part of `total()`; feedback buffers are no longer counted as render targets. The benchmark report has a new key `feedbackBytes`.
- Not run on a real graphics card or on Windows beyond the CI build; see `M-FBK-1`.
