# ADR 0014: Live sources: NDI input with discovery, cameras and capture cards, reconnecting, and a cheap upload path

- **Status:** Accepted (2026-11-20) as milestone 3 of [ADR 0012](0012-open-source-vj-platform-plan.md), implemented in v0.22.0. Issue [#49](https://github.com/MarlonXDev/NyrexVJ/issues/49).
- **Date:** 2026-11-20
- **Owners:** Maintainers (pending assignment)
- **Related:** [ADR 0007](0007-spout-receiver.md), [ADR 0010](0010-video-decode-pipeline.md), [ADR 0011](0011-render-pipeline-optimisation.md), [LIVE.md](../LIVE.md), [DEPENDENCIES.md](../DEPENDENCIES.md), [PERFORMANCE.md](../PERFORMANCE.md)

## Context
NyrexVJ could show files, generated looks and, on Windows, the picture of another program through Spout. A VJ also needs the picture of a camera, a capture card (a camera, a console, a laptop) and the picture of another computer on the network. The usual open standards for that are NDI for the network and the operating system's camera interface for devices.

Constraints that shaped the design:
- the program has to stay small and cheap next to VRChat, so an unused input must cost nothing, and a used one must not copy more data than necessary,
- no hard dependencies: the NDI library cannot be shipped (its licence), and FFmpeg is already an optional library that is opened at run time,
- sources come and go (a cable, a laptop that sleeps, a camera that another program takes), so a lost source is a normal state, not an error,
- the render thread never waits for a source (same rule as ADR 0010 and ADR 0007),
- the code must compile with GCC 11 and the Windows toolchain, and the logic must be testable without a camera, an NDI runtime or a graphics card.

## Decision
1. **One state machine for every live source** (`src/core/live_source.{hpp,cpp}`). `LiveStateMachine` has the states Searching, Connecting, Live, Signal lost and Reconnecting and a `ReconnectPolicy` (first delay 0.5 s, doubling up to 10 s, signal lost after 1.5 s without a picture, a forced reconnect after 3 s more, connect timeout 6 s). It is pure code with no thread, clock or library, driven by a time value, so the tests can walk through every transition. `LiveFrameBox` keeps only the newest frame, so a slow render never builds a queue and the picture on screen is never older than one frame. `LiveSource` is the common abstract interface (`stop`, `running`, `take`, `status`).
2. **NDI input** (`src/core/ndi_runtime.{hpp,cpp}`, `src/core/ndi_receiver.{hpp,cpp}`). The loader is shared with the existing NDI sender, which was rewritten on top of it (the sender tests are unchanged). NyrexVJ declares the few NDI structures it needs itself and loads the library at run time (`NYREXVJ_NDI_LIB` overrides the path), so there is no build dependency and no NDI header in the repository. `NdiFinder` is a reference counted discovery thread that runs only while a panel that lists sources is open or a receiver runs. `NdiReceiver` asks for the UYVY colour format with the "highest" bandwidth, drains the queue with a zero timeout and keeps only the newest picture (skipped pictures are counted as dropped), and copies a UYVY or UYVA frame as a tight UYVY picture (RGBA frames stay RGBA). Other FourCC codes and a UYVY width that is not even are reported as unsupported with a message instead of showing garbage. `pickNdiSource` takes the named source, or with Automatic the first source whose name does not contain the NyrexVJ output's own name.
3. **Cameras and capture cards** (`src/media/camera_capture.{hpp,cpp}`) through the FFmpeg device library (`libavdevice`), which is already the FFmpeg that video clips use: `video4linux2` on Linux, `dshow` on Windows. The device library is loaded like the other FFmpeg libraries, so without it only the camera clips say that cameras are not available. The requested mode (default 1280 x 720 at 30, or Auto for the device's own choice) is a hint; the device offers fixed modes and the closest is used. For modes above 640 x 480 at 30, MJPEG is tried first because it needs less bus bandwidth, then the camera's own format. A source name starting with `lavfi:` opens an FFmpeg test source instead of a device; it is used by the tests and the benchmark, because the build service has no camera. Opening has a deadline of 8 s and a read has a deadline of at least 2 s through the interrupt callback, so a device that hangs cannot block the stop of the thread.
4. **A cheap path to the graphics card.** Both sources hand over packed UYVY (2 bytes per pixel instead of 4 for RGBA; FFmpeg converts to UYVY with `sws` for cameras when needed, using the matrix and range that match the picture). The picture is uploaded as an RGBA8 texture of half the width and converted to RGB on the graphics card (`VideoGpu::convertPacked`, mode 3, limited range, BT.709 for 720 lines and above, BT.601 below). Compared with an RGBA upload this halves the bytes sent over the bus, and the processor does not convert anything. RGBA pictures of NDI go through the normal upload. The latency shown in the Clip window is the steady clock difference between the arrival of a picture in the capture thread and the end of its upload on the render thread.
5. **Zero cost when unused** (`src/render/live_input.{hpp,cpp}`, engine slots). There are eight clips: NDI Input 1 to 4 and Camera 1 to 4 (library filter Live). Like the Spout slots of ADR 0007, a slot is started when a layer shows its clip and released 3 seconds after the last use (`kLiveIdleSeconds`). Releasing happens on a worker (`std::async`), so closing a device never stalls a frame. An unused slot has no thread, no texture, no staging buffer and no open device. The chosen NDI source and camera per slot, and the camera mode, are saved in the program settings, not in presets (a preset stores only the clip by name, so it works on another computer with other devices).
6. **Clip window.** A live clip shows its state with a colour, the size and frame rate, the latency, dropped pictures and the number of attempts, a combo box for the source (NDI: Automatic or a name from the list, updated by the discovery thread; camera: None or a device, Refresh, resolution and frame rate), and a clear message when the NDI runtime or the FFmpeg device library is missing, with a button to download the NDI Tools. Everything goes through `tr()` (22 new texts with German, Spanish and French translations).
7. **Measurement and checks.** `--live-selftest` plays a lavfi source through the whole path (graphics card conversion, colour check at the centre pixel, release after the idle time, thread count back to the start) and compares the shader against a reference conversion on the processor; it runs in CI on Linux. `--bench-live SECONDS:camera:SOURCE` or `SECONDS:ndi:NAME` reports source rate, upload time, latency (average, 95th percentile, maximum), processor time and the memory of the slot.

## Alternatives
- **Link against the NDI SDK.** Rejected: the licence does not allow shipping it, and it would make the build fail without it. The loader with an own declaration of the few functions needed matches how Spout and the NDI sender already work.
- **A separate camera library per platform** (Media Foundation on Windows, V4L2 directly on Linux). Rejected for this milestone: FFmpeg's device layer is already loaded, covers both, and handles format negotiation. The price is less control over exotic devices. Direct back ends stay possible behind `LiveSource`.
- **Upload RGBA and convert on the processor.** Rejected: it doubles the bytes and costs processor time in the thread that VRChat also needs. The video path of ADR 0010 already measured a clear saving of processor time from converting on the graphics card.
- **A queue of pictures to smooth the rate.** Rejected: a queue adds latency, and a VJ prefers the newest picture. Dropped pictures are counted and shown.
- **Keep all eight slots running.** Rejected: an idle NDI receiver keeps a network connection and bandwidth up, an idle camera lights its LED. Slots start on demand.
- **Store the source in the preset.** Rejected: device names and network names differ between computers, and a preset must not point at a camera that is not there.

## Consequences
- Eight more clips in the library. Presets that do not use them are unchanged.
- The Windows 1 MB stack limit is a real risk for code that creates a `Composition` (41 KB) on the stack; the live self test allocates its composition on the heap.
- The device name lists differ by platform. Linux lists `/dev/video*` capture nodes through sysfs; Windows asks DirectShow through FFmpeg.
- When the signal of a source is lost, the last picture stays on the layer until the source returns; the placeholder look of the clip is shown only before the first picture. This avoids a flash of placeholder on stage, but a frozen frame can be mistaken for a live picture, so the state is shown in the Clip window only; a warning on the layer itself is open work.
- NDI alpha is assumed to be straight, not premultiplied. This is unverified against a real sender.
- An NDI sender that offers only a very high resolution, or UYVY with an odd width, is shown as unsupported.
- Latency is only measured inside NyrexVJ (arrival to upload). It does not include the camera, the cable, the network or the display.

## Validation
Everything below was measured on a software OpenGL driver (llvmpipe) with FFmpeg's `lavfi` test source and a fake NDI library, not with a real camera, a real capture card or the real NDI runtime. Numbers from a software rasteriser are not representative of a graphics card; the processor time excludes the rasteriser.

| Source | Source rate | Upload time | Capture to upload (average, 95th percentile, maximum) | Processor | Video memory of the slot |
| --- | ---: | ---: | --- | ---: | ---: |
| 1080p at 60 | 59.6 per second | 3.1 ms | 12.5 ms, 14.4 ms, 23.9 ms | 16.5 % of one core, including the generation of the test picture | 16.6 MB (8.29 output, 4.15 planes, 4.15 staging) |
| 720p at 30 | 30 per second requested | 2.3 ms | 19.5 ms average | 6.9 % of one core | 7.4 MB |

The latency of the 720p case is mostly the 33 ms between two pictures. Other checks:
- `nvj_live_tests` (135 checks: state machine, frame box, source selection logic, engine slots, release after idle, GPU memory returns to zero, threads return to the start value), `nvj_ndi_receive_tests` (173 checks against `tests/fake_ndi.cpp`: discovery, wanted and excluded names, formats, dropped pictures, lost source, reconnecting with the delays of the policy, an unsupported FourCC), `nvj_camera_tests` (121 checks with lavfi sources: sizes, rates, colours in 601 and 709, the `yuvj444p` range, device errors, a device that does not exist).
- Render loop regression: the default composition (`--bench-comp 25`, llvmpipe, three runs each, alternating) took 124.6, 126.7 and 127.8 ms per frame on `main` and 120.6, 134.8 and 121.2 ms on this branch, within the run to run spread of this software renderer.
- `--live-selftest`: the shader differs from the reference conversion by at most 1 level per channel (worst difference 0 to 1).
- The new tests also run clean under AddressSanitizer and UndefinedBehaviorSanitizer, the full suite runs with a 1 MB stack limit, and the changed files compile with GCC 11 and with MinGW (without the FFmpeg headers for the camera file).

Not validated, because the hardware was not available: real cameras and capture cards (format negotiation, MJPEG preference, hot plug), Windows DirectShow listing and opening at run time, the real NDI runtime (versions 5 and 6, alpha, other colour formats, several senders), real latency end to end, graphics card timings, and the effect on VRChat. Please report measurements from real computers with `--bench-live`.
