# ADR 0042: Hot standby for two PCs with readiness checks, a confirmed takeover and an epoch that makes the old master yield

- **Status:** Accepted for the local part (requested by MarlonXDev as prompt 21). Issue [#112](https://github.com/MarlonXDev/NyrexVJ/issues/112). Switching of video paths (projectors, matrices, NDI routes), a third PC, a shared timeline, a vote between PCs, encryption and a test on real hardware are **not built**.
- **Date:** 2026-11-25
- **Owners:** Maintainers (pending assignment)
- **Related:** [SYNC.md](../SYNC.md), [ARCHITECTURE.md](../ARCHITECTURE.md), [INTERFACES.md](../INTERFACES.md), [PERFORMANCE.md](../PERFORMANCE.md), [ADR 0041](0041-multi-pc-sync.md), [ADR 0034](0034-show-packages.md)

## Context
[ADR 0041](0041-multi-pc-sync.md) lets a second PC follow a master. A follower that keeps up is already a warm copy of the show, but nothing used that: when the master crashed or its network cable was pulled, the follower held its last values and waited, the person at the desk had to notice, change the role by hand and tell the controllers where to connect. Prompt 21 asks for a hot standby that is ready before it is needed, that proves its readiness with checks, that can take over by an explicit action or, if the user turns it on, by itself, that never takes over the outputs or the network without protection against two PCs playing at once, and whose recovery time and data loss are criteria that can be measured and are not promises.

## Findings (what existed before)
- **Existed:** the session file (`saveSession`, written about every 30 s when the composition changed) and the rotating autosave (every 120 s when the composition changed, listed by `listAutosaves`) with the crash dialog on the next start (`previous_.crashed`, `recoveryEntries_`); the crash handler and the crash report; the multi output manager with the frame lock, a delay per output and the swap skew measurement; the master and follower protocol of ADR 0041 with a clock, a state vector, a manifest of clip names, Hello with a backoff and a follower state machine (Connecting, Getting the state, In sync, Lost); the control router with 150 targets; the engine with layers that can fail to open a clip (`MediaPlayer` state Failed, `clipError`); the show package for putting the same files on every PC; the test machinery with `ctest`, in process self tests, two process scripts and CI.
- **Existed, not enough:** a lost master only turned the follower into `Lost` and nothing else; a session snapshot is about the file on the same PC, so a PC that died took its snapshot with it; the manifest told a follower that a clip is missing but did not say whether the show as a whole matches; nothing said whether a decoder on the standby had failed or whether its output windows were open; the master did not know in what state its followers were.
- **Not found:** any health report between the PCs, any notion of who leads (an epoch or a term), a way to hand the lead over, any rule for the old master returning, and any measurement of how long a takeover takes.
- **Not verified before this version:** what happens on a real network when the master PC is switched off or its cable is pulled, a real projector or capture card on the standby, a real video switcher, and every case with a third PC.

## Decision
1. **Reuse the sync protocol, add the smallest extension.** The standby is a follower of ADR 0041 with the option Use hot standby turned on. Protocol version 2 adds a message `Takeover` (type 12) and an optional tail on two existing messages: Clock gets an epoch (4 bytes), a health byte (1) and a 64 bit show fingerprint (8), 13 bytes at 10 beacons a second; Ping gets a readiness byte (1), a health byte (1) and the fingerprint (8), 10 bytes once a second. The Hello packet itself still carries header version 1 and lists the range 1 to 2, so a master of v0.48.0 accepts a v0.49.0 follower; negotiation picks the common version, and the tails are only sent when both sides speak 2. Nothing in the state vector, the delta, the keyframe or the manifest changed.
2. **Health and readiness travel on the existing messages.** Health bits: 1 a decoder failed, 2 an output the user wants is not open, 4 overloaded. Bits 1 and 2 are set by the failover system; bit 4 is defined, carried and tested in the protocol, but nothing sets it yet. Readiness: Unknown, Ready, Degraded, Not ready. The master shows what each follower reports; the standby sees the health of the master. Only the numbers and the names of the problems travel, never media.
3. **A show fingerprint instead of trust.** The fingerprint is a 64 bit prefix of a SHA-256 over the names of the used decks and the clip names in the cells of those decks. Two PCs with the same fingerprint have the same names in the same places, which is what the standby must be able to play. It is a check on names; it does not prove that two files with the same name have the same content (that is what a show package is for) and the page says so.
4. **Eleven readiness checks, each Ok, Warn or Fail with a text.** Link (connected and in sync), version (Full compatibility: the same list of controls, so the standby gets the whole state), clock (round trip under 50 ms and jitter under 15 ms), state (a state that is at most 1 s old), assets (no clip missing, differences only warn), files (a clip file of this PC is missing on its disk), show (fingerprint equal; unknown only warns), outputs, decoders (no playing layer with a failed clip), primary (the master reports no fault) and snapshot (the last session snapshot of this PC is at most 150 s old). A single Fail makes the standby Not ready and blocks the automatic takeover. The output check is deliberately conservative: when the user wants outputs (output 0 is always on in settings) and no window is open, the check fails, because a standby that could not show a picture is not a standby.
5. **A state machine that is separate from the sync code.** `failover::Machine` (`core/failover.*`, no sockets, no OpenGL, a clock that is passed in) has the states Idle, Connecting, Following, Primary unhealthy, Primary lost, Primary ended, Confirm pending and Leader. The sync system only gives it facts and carries out what it decides. This is what the 144 checks of `nvj_failover_tests` run against.
6. **A takeover has one of two causes and one gate.** The user can ask for it (the button Take over... asks again and, if the primary still answers, warns that two PCs would play). The standby can ask by itself, but only if the user ticked Take over automatically, the standby is armed, and all of these are true: the standby was Ready (no Fail) for at least 10 s before the loss, no clean Bye arrived, no decoder fault and no missing output on this PC, and no automatic takeover was used since it was armed (**one shot**, Arm again resets it). The lost-after time is a setting, default 5 s, 3 to 60 s. A master that closes the program normally sends Bye and the standby says Primary ended and does not take over by itself: the person closed it on purpose. Both causes end at the same gate; a manual takeover while the primary is alive is a two step action with the warning.
7. **An epoch decides who yields.** Every master has an epoch (1 for a normal start). The leader that takes over uses the epoch of the lost master plus 1 and puts it in every beacon. A `Takeover` message is signed with the same key as everything else and carries the epoch, the port of the new leader and its name; a master accepts it only if the epoch is higher than its own and higher than any it saw. A master that receives one **steps down**: it sends Bye with the reason Superseded to its followers and becomes a follower of the new leader. The new leader announces to the old master's host and port (backoff up to 5 s) until the old master has joined as a follower. The epoch is shown on the page and in the report, so a person can see which PC leads and in which round. A Takeover with an epoch that is not higher than the master's own, or than one already seen, is ignored, so a repeated or old message cannot make a current leader step down. The stray guard also stops two masters from answering each other's Reject for ever.
8. **Outputs of the standby are held black, and a takeover opens nothing.** While a PC follows as a standby, its master output is multiplied by 0 (`Engine::holdOutput`; it affects the master output texture, the output windows, NDI, Spout and the recorder, not a per layer route), so a projector that is connected cannot show a second picture; the option can be turned off. A takeover **never** opens windows, changes monitors or touches a switcher: the output windows must already be open on the standby. The held output is released when the state is Leader.
9. **No automatic takeover of the network or the controllers.** OSC, MIDI and the REST interface are not moved; the leader serves followers on the port that the setting Port as leader names (0 = the same port as the old master), and the page shows the address. A controller that talks to the old master has to be pointed at the new one by the person or by the controller's own setting. This is on purpose: moving the control path without a person is the risky part.
10. **RTO and RPO are criteria with a definition, not promises.** RTO: the time from the last packet of the old master to the moment the leader answers a follower, split into detection (the lost-after time plus at most a frame), decision (zero for automatic, the time of the person for manual) and serving (the time from the decision to the leader socket answering). RPO: the age of the newest state the standby had when it took over, bounded by the delta interval (1/30 s), the network time and a frame, and by lost packets (the tail check after 0.4 s asks for a resync). What is **not** in the RPO: media, the position of the timeline, presets, settings, the state of the cue list, and any change the master made in the last packets that did not arrive. The numbers are in Validation and are the numbers of one machine with software rendering.
11. **Two PCs, a human at the desk, an external switch for the pictures.** There is no third voter. During a real network split both PCs may think they lead (the standby sees a master that is lost, the master sees nothing wrong). NyrexVJ does not switch video; a seamless change of what the audience sees needs a video switcher, matrix or NDI router that selects one of the two PCs (see [SYNC.md](../SYNC.md)). The epoch is the rule by which, when the network is back, the old master yields to the leader with the higher epoch; that was tested with a frozen and resumed primary, and a real split of a network was not.
12. **Safe defaults and tests as part of the design.** Everything is off: no use of the standby, no automatic takeover; the lost-after time, the black hold and the leader port have defaults that change nothing for a user who never opens the page. `--failover-selftest` runs the real engine through readiness, loss, takeover, step down, clean close and a decoder fault; `scripts/test_failover_two_instances.py` runs two and four real programs with a frozen process, a killed process and a closed process.

## Alternatives considered
- **A third PC or a quorum.** The only way to decide a network split by software. It needs hardware and a protocol for a vote that nobody asked for; the epoch plus a human decides in this version.
- **Switch the video path from inside NyrexVJ.** Would need drivers for matrices, switchers and routers, each with its own commands, and a real device to test; it would also be the first thing that can put a wrong picture on a projector. Not built, documented as a requirement.
- **A virtual IP or a floating address.** An operating system feature, outside the program, and it would hide the takeover from the person.
- **A second protocol for health.** More ports and more rules for a few bytes. The optional tail on the existing messages is cheaper and keeps the signature.
- **Replicating the media or the whole project.** Large, slow and the wrong direction: the show package already moves files before the show.
- **Automatic takeover on by default.** Rejected: a takeover that nobody asked for is a surprise at the worst time. The user opts in, and the one-shot rule stops a flapping network from handing the lead back and forth.
- **Taking over when the primary says Bye.** Rejected: a clean close is a decision.

## Consequences
- New files `core/failover.*`, `app/failover_system.*`, `app/failover_selftest.*`, `app/ui_failover.cpp`, `tests/test_failover.cpp`, `scripts/test_failover_two_instances.py`. `netsync.*` gets protocol version 2 (the epoch, health, readiness and fingerprint tails, `Takeover`, Bye reason), `NetSyncSystem` gets the epoch, an override of its own settings while it leads, `becomeLeader`, `stepDown` and the takeover notices, `Engine` gets `holdOutput` and `playingFaults`, `App` a menu item Output, Hot standby... and the window.
- New settings keys `failoverEnabled`, `failoverAutoTakeover`, `failoverLostAfter`, `failoverHoldOutputs`, `failoverLeaderPort`. New start options `--failover-selftest`, `--failover-report FILE`, `--failover-takeover-at SECONDS`.
- The interface texts are in all eight languages (93 keys).
- A follower that speaks only protocol 1 (the v0.48.0 follower) gets a Welcome with protocol 1 and clocks without tails from a v0.49.0 master; `nvj_netsync_tests` runs that case with a hand made protocol 1 Hello. The other direction (a v0.49.0 follower against a v0.48.0 master) follows from the Hello rules of ADR 0041 but was not run with a real v0.48.0 program. Readiness and health only travel when both sides speak protocol 2: against a v0.48.0 master the Show check can only warn (no fingerprint arrives) and the Primary check cannot see a fault. A v0.48.0 master does not know the Takeover message and would not step down; that combination was not run.
- Marking a PC as standby holds its master output black. The user who uses a follower as a second picture must leave Use hot standby off (the default).

## Validation / open questions
- Done here, on Linux with the Mesa software renderer (llvmpipe, no graphics card), on a container with two cores: `nvj_failover_tests` (144 checks, a pure state machine with a simulated clock: thresholds, one shot, clean close, decoder fault, manual two step, epoch rules), `nvj_netsync_tests` (10,493 checks, now with the protocol 2 negotiation and the tails against a v1 peer), `nvj_control_tests` (619, the new settings), `--failover-selftest` (74 checks in the real engine, two runs after the last change, 74 of 74 each), `--netsync-selftest` (64) and `scripts/test_failover_two_instances.py` (32 checks, two and four real programs with `--output`), the whole `ctest` suite of 48 tests, the translation check and the start of the program. One check of the self test was timing dependent (the readiness reaches the primary once a second); it now waits up to 3 s for the message instead of 0.5 s.
- Measured here: automatic takeover decided 3.02 s after the last packet with the lost-after time set to 3 s (the minimum; the default 5 s was not measured, the rule gives the same plus 2 s); the leader answered a follower 0.035 to 0.13 s after the decision (self test and real programs, four runs); a frozen primary (SIGSTOP) became a leader after 3.2 to 3.6 s and a killed primary (SIGKILL) after 3.3 to 3.5 s, observed by a script that polls a report file every 0.5 s, so these are upper bounds with a resolution of half a second; the standby was ready 10.5 s before the loss; a fader move 0.15 s before the kill was present on the leader; the output of the standby was 0.0 brightness while held and 167.8 against 169.6 before as the leader; the update step of the failover system costs 12.6 and 13.1 microseconds on average (131 and 647 microseconds worst case) in two self test runs; the extra bytes are 13 per beacon and 10 per ping by the encoders (about 140 bytes a second on top of the 1.2 kB/s of an idle follower, computed from the encoders and not measured on a link).
- **Not done:** a real network (the loss in the tests is a SIGSTOP, a SIGKILL and a clean close of a process on the same PC, not a pulled cable or a switch that dies; a partition of a real network was only simulated by freezing the process), two real PCs, a real projector or capture card on the standby, a real video switcher, matrix or NDI router, a graphics card, hardware decoders that fail in their own ways (the decoder fault in the tests is an image file that cannot be read), Windows at run time, an event of hours, a power loss, and a review by someone else. The recovery times above are those of a loopback network with software rendering at 8 to 13 frames per second; a show at 60 frames per second should be at least as good, which was not measured.
- **Open limits, known:** during a real network split both PCs may play; the beat clock of the leader goes on from where the follower had it when the network source ended, and whether the beat stays steady at that moment on a real show was not measured; the old master that comes back is told by a repeated message, so one that comes back with a changed key or another address is not told; the standby follows the master's layers by clip name and not by file, so two files with the same name pass the show check; the output check cannot tell a closed window from one on a switched off projector; media, the timeline, presets and settings are not replicated.
- **Open for the maintainer:** whether a third voter (a small tie breaker program) is wanted, whether a video switcher integration for one device family (Blackmagic ATEM, a Kramer matrix, NDI Access Manager) should come next with a real device to test against, whether the automatic takeover should be allowed to run twice, whether the standby should send a periodic copy of the session file over the network, and whether the controller addresses should be taken over (they are not).
