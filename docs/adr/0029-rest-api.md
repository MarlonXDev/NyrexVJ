# ADR 0029: An optional local web interface and REST API: off by default, one background thread, a snapshot for reads and a bounded queue for writes, a token and the checks a browser needs

- **Status:** Accepted (requested by MarlonXDev, Prompt 06). Issue [#84](https://github.com/MarlonXDev/NyrexVJ/issues/84). TLS, saving and deleting presets, changes to the structure of a composition, recording control, file upload, events or WebSocket, several users with different rights and any discovery are **Proposed** and wait for the maintainer.
- **Date:** 2026-11-25
- **Owners:** Maintainers (pending assignment)
- **Related:** [API.md](../API.md), [INTERFACES.md](../INTERFACES.md), [TESTING.md](../TESTING.md), [PERFORMANCE.md](../PERFORMANCE.md), [ADR 0008](0008-osc-output-protocol.md), [ADR 0016](0016-show-sync.md), [ADR 0027](0027-live-stability-and-hardware-test-matrix.md)

## Context
The request: an optional, **disabled by default** local HTTP API for status, clips, decks, layers, effects, presets and outputs, a lean web interface on top, no open network interface without explicit approval, token authentication, an Origin check, rate limits and thread safety, a versioned API with tests and documentation. It must reuse the existing control target logic, must not be confused with show sync over several computers (Prompt 20) or shared editing (Prompt 33), and must never block rendering with network or file work. A large change of the architecture needs a maintainer decision.

## Findings (what existed before)
- **OSC input** (`src/control/osc.*`, UDP, polled on the main thread, off by default, port 9010, optional remote) and **MIDI input** both end in `ControlSystem::fireTarget` over the control ids of `controlTargets()` (`master/level`, `layer/N/opacity`, `column/N`, `deck/N`, ...). The cue list and the OSC output name controls by the same ids. This is the one control logic.
- **No HTTP, no TCP server, no token, no random number source of the operating system.** The only sockets were UDP (`udp_socket_*`). A JSON library was already there (`nlohmann/json`, used for presets and settings).
- **State is owned by the main thread.** `Engine`, `Composition`, the clip and effect libraries (mutable globals) and `ControlSystem` have no locks and are used only from `App::frame`. The plugin system already follows the rule that other threads hand work to the main thread.
- **Presets.** `loadUserPreset` reads a file and builds a `Composition` in one step. `compositionFromJson` reads the global libraries, so it may only run on the main thread.
- **Settings** are read tolerantly and may gain keys; `settings.json` is the file people attach to bug reports.

## Decision
1. **Off by default; local by default.** Three settings (`apiEnabled`, `apiPort` 1024 to 65535, default 9020, `apiAllowRemote`). With the interface off no socket exists and the per frame cost is a boolean. The server binds `127.0.0.1`; `0.0.0.0` only with the explicit option, which shows a warning on the Settings page. On Windows the port is opened with `SO_EXCLUSIVEADDRUSE`. NyrexVJ never touches a firewall, a router or a discovery protocol.
2. **One extra thread at background priority, no thread per client.** A poll based state machine (`src/control/api_server.*`) accepts, reads, answers and closes; every connection answers once and closes (`Connection: close`), which removes keep-alive state, request pipelining and most smuggling. It is HTTP/1.1 only, written for this purpose: a socket wrapper (`tcp_socket.hpp`, POSIX and Windows files), a strict parser (`src/core/http_message.*`) and a router (`api_router.*`) that can be tested without a socket. No new dependency.
3. **The server never touches the engine.** Reads come from an immutable `shared_ptr<const Snapshot>` that the main thread builds every 0.25 s and after each command (`ApiSystem::buildSnapshot`, about 9 µs). The clip and effect libraries are copied into the snapshot and only re-copied when their signature changes, because the libraries are mutable globals. Writes go into a bounded queue of 64 commands (`Hub`); the main thread runs at most 16 per frame, at the start of `App::frame`, through `ControlSystem::fireTarget` (the same path as OSC and cues). The result comes back through a `Ticket`; the server polls it without blocking and, after one second, cancels the request and answers 503 `busy`. A cancelled command is never run later. A stuck main thread cannot hold the server, and the server cannot hold the main thread.
4. **Presets are split along the thread line.** The server thread lists and reads the file (`listUserPresets`, `readUserPresetText`); the main thread parses it (`parseUserPreset`) and applies it. `loadUserPreset` keeps its behaviour as the composition of the two. A name must equal `sanitizePresetName(name)` and be in the listing, so a path cannot get in. A damaged file gives 422 and changes nothing.
5. **API v1 is small and follows the control ids.** Status, controls (all ids, read and write), layers, clip trigger, layer clear, column trigger, decks, clips, effects, presets (list, load) and outputs. A write to `/controls/{id}` takes the same ids as OSC and the normalised value 0 to 1 (`true` and `false` for switches); there are no second names. Errors have a code and a message. Additions inside v1 are compatible, a change that breaks a client raises the number in the path (`/api/v2/`).
6. **Token authentication.** 256 random bits from the operating system (`BCryptGenRandom`, `/dev/urandom`; failing to get them keeps the interface off), `Authorization: Bearer`, constant time comparison. The token lives in its own file `api_token` (0600 through a temporary file and an atomic rename on Linux), not in `settings.json`, and is never logged. The page itself is served without the token and carries none; the token reaches it in the URL fragment, which the browser does not send, and the page moves it to `sessionStorage` and removes it from the address.
7. **The checks a browser needs.** `Host` must be a local name or, with remote access, an IPv4 address, and have the right port (DNS rebinding); `Origin` must equal the server; `Sec-Fetch-Site` must be `same-origin` or `none`; no CORS headers, so preflights fail; JSON only with `Content-Type: application/json`; only GET, POST and PUT. The page gets a Content-Security-Policy that allows only itself (no inline script or style, no framing), `no-store`, `nosniff`, `X-Frame-Options: DENY` and `no-referrer`.
8. **Rate limits and bounds.** 40 requests a second per address (burst 80), five wrong tokens in 60 s lock the address for 60 s, 32 connections (8 per address), 256 remembered addresses, a header up to 8 KiB and 48 lines, a body up to 64 KiB, an address up to 2048 bytes, JSON depth 12, 5 s for the header and 10 s for the request. The parser refuses chunked bodies, `Expect`, duplicate `Host` and `Content-Length`, bare line feeds, NUL and path tricks.
9. **A page, not a framework.** `/`, `/app.js`, `/app.css` and `/lang.json` are compiled into the program as text (no files to install, no build step, no external request). The script builds the page with `textContent` only. The text is in the eight languages of the program and follows `navigator.language`; a test compares the keys of all languages and the keys the script uses.
10. **Options for testing.** `--api-selftest` runs the interface against the real engine, `--bench-api [FRAMES]` measures the frame time with the interface off, idle, with polling clients and under a flood. `scripts/test_web_ui.mjs` checks the page in Chrome.

## Alternatives considered
- **A third party HTTP library (cpp-httplib, Boost.Beast, civetweb).** Each is bigger than this server, brings its own thread model (a thread per client or a pool), and the checks that matter here (strict parsing, Host and Origin, the snapshot and queue rule) would still be ours. A new dependency also needs a licence and supply chain review. Kept as an option if the maintainer prefers a library for HTTP/2 or TLS.
- **Locking the engine and calling it from server threads.** Every existing access would need a lock and the render thread would wait for network threads. The snapshot plus queue costs a copy a few times a second and keeps the render thread free.
- **Putting the token in `settings.json` or in the page.** Settings files get attached to bug reports, and a token in the page is a token for everyone who can open the page.
- **A cookie session or a login form.** It adds state, CSRF handling and a login page for one user on one machine. A bearer token in a header cannot be sent by another site's form.
- **CORS with an allow list.** It would let another site's script talk to the program. Without CORS headers the browser keeps the answer from other sites.
- **WebSocket or server sent events for live values.** Polling twice a second is enough for a control page, needs no upgrade handling and no per connection state, and is bounded by the rate limit. Left open.
- **TLS.** A certificate for a local address is either self signed (a browser warning on every device) or needs a name and an authority; it also needs a library. Left to the maintainer. The page says the connection is not encrypted.
- **Editing the structure of a composition and saving presets.** These change what a show is, are harder to undo in the middle of a show and need their own checks. Not part of v1.
- **mDNS or other discovery.** It announces the program to the network without being asked.

## Consequences
- A new listening socket exists only when a person turns it on, and on the local address unless they turn on remote access.
- The main thread gains a bounded amount of work (at most 16 commands and a snapshot every 0.25 s); the measured cost was a few microseconds a frame, and an update with the interface off is a check of one flag.
- A stalled main thread shows up as 503 `busy` for writes while reads keep answering from the last snapshot.
- A `Settings` change in the three keys is applied at once (restart of the server); a failed start is shown and can be retried.
- Plugins and other code must not call `ApiSystem`; the control ids remain the one interface to controls. Renaming a control id still breaks OSC, MIDI mappings, cues and now this API, and belongs in the changelog under its own line.

## Validation / open questions
- Done here: `nvj_api_tests` (21,016 checks), `--api-selftest` (59 checks), the page in Chrome (46 checks), AddressSanitizer, UndefinedBehaviorSanitizer and ThreadSanitizer, the frame time measurement in [API.md](../API.md).
- **Not done:** `--api-selftest`, the page in a browser and the exclusive port on Windows (the unit tests, including the real server on Winsock sockets, passed in the Windows CI), a run on a real graphics card, on a phone or tablet, with a second computer on a network, next to VRChat, or for hours. The load generator in `--bench-api` runs inside the same process, so the flood number is an upper bound on a two core machine.
- Open for the maintainer: TLS, the scope of write access (presets, composition structure, recording), events, whether a read only token is wanted, and whether the page should offer a QR code with the address (it would put the token in an image).
