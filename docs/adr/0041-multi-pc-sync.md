# ADR 0041: Multi-PC show synchronisation with a signed master and follower protocol on top of the beat clock

- **Status:** Accepted for the local part (requested by MarlonXDev as prompt 20). Issue [#110](https://github.com/MarlonXDev/NyrexVJ/issues/110). Automatic discovery, encryption, a shared timeline, shared editing (prompt 33), backup output switching (prompt 21), IPv6 and a hardware frame lock (prompt 12) are **not built**.
- **Date:** 2026-11-25
- **Owners:** Maintainers (pending assignment)
- **Related:** [SYNC.md](../SYNC.md), [ARCHITECTURE.md](../ARCHITECTURE.md), [INTERFACES.md](../INTERFACES.md), [PERFORMANCE.md](../PERFORMANCE.md), [ADR 0008](0008-osc-output-protocol.md), [ADR 0016](0016-show-sync.md), [ADR 0029](0029-rest-api.md), [ADR 0034](0034-show-packages.md)

## Context
Two PCs that run NyrexVJ for one show (a second output for another projector, a second machine for a heavy layer, a backup that should stay warm) had no way to follow each other. The beat clock followed tapping, audio, MIDI clock, timecode and Pro DJ Link, but no other NyrexVJ. OSC output sent single values one way without a state, a sequence number or a check of who sends. A show is more than a beat: levels, effects, macros, which clip plays on which layer and which deck is active all have to land on the second PC, and they have to land again after a network drop. The media files themselves are far too big to send, and every PC has its own copy of them.

## Findings (what existed before)
- **Existed:** `BeatClock` with a source priority and a phase observation interface (`report`), `SyncSystem` with MIDI clock, LTC, MTC, Pro DJ Link and the cue list, `ControlRouter` with 150 control targets and one address per target (`/nyrex/<id>`), the `UdpSocket` wrapper (shared and exclusive modes in later versions), a token file for the REST interface (`api_security`), settings with defaults and range checks, the show package format for moving files, and a test machinery with `ctest`, in process self tests and CI.
- **Existed, not enough:** OSC output has no session, no order, no authentication and no snapshot, so a PC that joins late or loses packets stays wrong. The REST interface is for one controlling client with a token and does not carry a clock. A show package moves files, not a live state.
- **Not found:** a network clock source, any versioned protocol between two NyrexVJ programs, a message authentication on UDP, a state snapshot with incremental updates, a rule for reconnecting, a clock offset and drift estimate.
- **Not verified before this version:** behaviour on a real network with a switch, Wi-Fi jitter, a firewall in the way, Windows sockets at run time, and anything with three or more real PCs.

## Decision
1. **A new clock source, not a new clock.** The follower reports a phase observation (`SyncSource::Network`) to the existing `BeatClock`, with the predicted master beat and tempo, once per frame. The clock keeps its smoothing, its lock states, its latency offset and the rule that a large phase error is corrected gradually. In `Automatic` the network is the first source of the priority list, before Pro DJ Link, and it only counts while a master is live. A PC set to `Manual` that follows the master takes `Network` while the option Follow beat, tempo and timecode is on. A PC with another fixed source (Pro DJ Link, MIDI, LTC, MTC, Audio) keeps it and the page says that the network clock is not used. The master timecode arrives as a fifth timecode source (`Network`), so cues and the timecode modulators work on a follower.
2. **One UDP protocol, versioned, signed.** Datagrams of at most 1200 bytes, a header of 26 bytes (magic `NVJS`, protocol version, type, session id, sequence number) and a 16 byte HMAC-SHA256 tag over the whole packet with a shared 256 bit key. Messages: Hello, Welcome, State, Delta, Clock, Ping, Pong, Resync, Manifest, Bye, Reject. A packet with a wrong tag is counted and never answered, so a stranger on the network learns nothing and the master cannot be used to reflect traffic. Replies, including Reject, go only to authenticated Hellos. The key is made from the system's secure random source, stored in `netsync_key` in the data folder (private to the user on Linux and macOS, with the permissions of the folder on Windows, like the REST token) and shown only on the master, hidden until you ask. A check code (a short hash of the key, not part of it) lets two people compare keys by voice. The protocol is **signed, not encrypted**: a listener on the network can read the show state but cannot change it or join.
3. **Negotiation instead of hoping.** The Hello carries the lowest and highest protocol the follower speaks and a hash of the list of synchronised control ids (the schema). The master answers with the protocol to use and one of three states: Full (same schema), Clock only (same protocol, different layout of controls, so only the beat is followed and the page says why) and Refused (no common protocol version, with a Reject that names the reason). A new NyrexVJ with new controls therefore never writes a value into the wrong control of an older one.
4. **A state vector with a snapshot and deltas.** The show state is a vector of floats: 150 controls (every control that is not a trigger and not the tempo, because the tempo travels with the clock), the active deck, the active column of each layer and a counter per layer that grows with every clip start (159 values). A State message is the whole vector, a Delta lists only changed indices (at most 60 per message, at most every 1/30 s), and a keyframe goes out every 5 s. Every packet from the master has a sequence number that only grows. A follower drops duplicates and old packets, notices a gap, asks for a resync and keeps asking until a State arrives, and a master that stopped sending after a loss is noticed by a tail check (0.4 s) so a lost last packet does not leave the follower wrong for ever. Hellos and Welcomes repeat with a backoff of 0.5 to 5 s until the handshake is confirmed.
5. **Clock sync that handles jitter and drift.** The master sends a Clock beacon every 0.1 s with the beat, tempo, bar length, play state, lock flag, timecode, a jump counter and a cue counter. The follower pings once a second and keeps the last 40 round trips. It takes the lowest third by round trip time (between 3 and 12 samples), uses their mean as the offset and fits a drift (a slope) only when those samples span at least 10 s and the slope is more than three standard errors away from zero, clamped to plus or minus 200 ppm. Without that test noise on a quiet network was fitted as drift. The predicted master beat is the beat of the last beacon plus the time since then times the tempo, while the master plays. A jump of the beat on the master is detected from the beat itself (it moved more than the tempo explains) and counted in the beacon, so the follower jumps too and does not slide.
6. **Conflict rules, written down.** (a) The master wins: a value that changes on the master is applied on every follower. (b) The first connection applies the full state. (c) After a reconnect only the values that changed on the master since the follower saw them are applied; a value the user edited on the follower and that did not change on the master stays. (d) While the follower follows the controls its own timeline and cue list are paused so that they do not fight the master. (e) When the master is lost (3 s without packets) the follower holds the last values, lets the tempo run at the last value and reconnects on its own. (f) Followers never change the master: they send only Hello, Ping, Resync and Bye. (g) A deck switch is applied before the controls that came with it, so they land in the new deck. (h) A clip start is a counter that grew, so the same clip started again restarts. (i) Only the three ticks Follow the controls, Follow decks and clips and Follow beat, tempo and timecode decide what a follower takes over, and each can be off.
7. **Media never travels, and a difference is shown.** The master sends a manifest: the names of the used decks and the names of the 32 clip cells of the active deck (at most 60 bytes each, 16 entries per message), every 5 s and when it changes. A follower compares it with its own library and shows: a clip that only exists on the master, a cell that holds another clip here, a deck that is not in use here, a deck with another name. A clip is **not started** when the local cell has another name than the master's, a deck is not switched when it is not in use here, and nothing is guessed. The way to get the same files on every PC is a show package ([ADR 0034](0034-show-packages.md)) or copying the folders.
8. **Safe defaults.** Off. With the role Off no socket is opened and no key is made. A master listens on the loopback address only until Allow other PCs in the network is ticked, and the page then says that the port is open to the network. A follower connects to the IPv4 address that you type and to nothing else, so discovery (broadcast or multicast) is **not built** on purpose: it would open a port that answers strangers. The key is not part of settings or presets, not in logs and not in a package. A master serves at most 8 followers, limits each address with a token bucket (400 packets a second, a burst of 800), remembers at most 64 clients for replay protection and 256 buckets, and a flood of packets with a wrong tag costs a hash and a counter.
9. **No hardware frame-sync claim.** The protocol aligns the beat of each PC to the beat of the master. Each PC draws at its own frame time, so two outputs can differ by about one frame, and graphics cards, displays and projectors add their own delay. What a follower measures and shows is offset, round trip time and jitter of the network clock. Hardware genlock is a separate, optional prompt (12) and is not built.
10. **Tests are part of the design.** The protocol core is a pure library with an injected clock and random numbers (`core/netsync.*`, no sockets, no OpenGL), so it is tested with a simulated network that loses, duplicates, reorders, delays and cuts packets (`core/netsync_link.hpp`). The show layer, the UDP transport and the glue are tested separately, and `--netsync-selftest` and `scripts/test_netsync_two_instances.py` run the real engine and two real programs.

## Alternatives considered
- **OSC both ways.** Already exists and is simple, but has no session, no order, no snapshot, no authentication and no clock estimate. Making that safe would have meant putting a protocol inside OSC messages. Rejected; OSC stays the interface for controllers.
- **Ableton Link.** A good fit for a shared beat but not for a show state, and a licensed dependency for a feature that needs a state anyway. Not built.
- **PTP or NTP style time over UDP only.** The ping and offset estimate is a small NTP style exchange on purpose, with minimum round trip filtering. Full PTP needs hardware time stamps to be better than a frame.
- **TLS or DTLS.** Real encryption needs certificates or a handshake with a library. The first version signs everything, documents that it is not encrypted and keeps the key private. An authenticated and encrypted transport is the obvious next step.
- **Discovery by broadcast.** Convenient, but it answers anyone on the network and is blocked on many switches. Typing an address is a small price.
- **TCP.** Delivers in order but delays everything behind a lost packet, which is the wrong trade for a beat. Sequence numbers, deltas and keyframes give the order that matters without the stall.
- **Sending the media.** Out of scope and would make the show depend on the network at the worst time.

## Consequences
- New files `core/netsync.*`, `core/netsync_link.hpp`, `control/netsync_key.*`, `control/netsync_show.*`, `control/netsync_transport.*`, `app/netsync_system.*`, `app/netsync_selftest.*`, `tests/test_netsync.cpp`, `tests/test_netsync_show.cpp`, `tests/test_netsync_transport.cpp`, `scripts/test_netsync_two_instances.py`. `BeatClock` has a `Network` source, `SyncSystem` a network timecode, `Engine` a trigger counter per layer, `ControlSystem::setTarget`, `UdpSocket` exclusive open and addressed send and receive, and Settings, Sync has a section Network sync.
- New settings keys `netSyncRole`, `netSyncPort`, `netSyncAllowRemote`, `netSyncHost`, `netSyncName`, `netSyncFollowControls`, `netSyncFollowClips`, `netSyncFollowClock`. Defaults leave everything as before: the program opens no new port and writes no key.
- New start options `--netsync-selftest`, `--netsync-report FILE` and `--run-seconds N`.
- A follower pauses its own timeline and cues while it follows the controls. This is on purpose and the page says so.
- The protocol version is 1. A change that cannot be read by version 1 raises it, and the Hello range keeps older and newer programs talking in Clock only mode or refusing with a reason.

## Validation / open questions
- Done here, on Linux with the Mesa software renderer: `nvj_netsync_tests` (10,370 checks, a simulated network with loss, duplication, reordering, jitter, drift, outages, wrong keys and hostile packets), `nvj_netsync_show_tests` (540), `nvj_netsync_transport_tests` (105, real UDP sockets on the loopback address with a lossy relay, a master restart and a wrong key), `nvj_beat_clock_tests` (118, with the new source), `--netsync-selftest` (64 checks in the real engine in both roles) and `scripts/test_netsync_two_instances.py` (27 checks, two real programs, 25 percent loss, up to 25 ms of added delay and a 6 s outage), the whole suite of 47 tests, the translation check and the start of the program.
- Measured here: the beat of a follower stayed within 2 to 17 ms (mean) and 31 ms (worst) of the master with two real programs on one computer, including the lossy phase and after the outage; the update step of the sync system costs 10 to 18 microseconds a frame; one follower costs about 1.1 kB/s (12 packets a second) while nothing changes and about 2.9 kB/s while three faders move. Two programs with software rendering ran at 8 to 13 frames per second, so these errors are dominated by the frame time and a 60 frames per second show should do better, which was not measured.
- **Not done:** a real network (switches, Wi-Fi, a firewall, a second network segment, packet loss from a real link), three or more real PCs, Windows at run time (the socket code was built in CI but not run; the two-process test was only run on Linux), a graphics card, a show with hours of runtime, differing program versions on two real PCs, and a security review by someone else. The signature gives integrity and sender authentication under the assumption that the key is private; it gives no secrecy, and a recorded packet can be replayed only within the sequence window of a live session.
- **Open for the maintainer:** whether an encrypted transport is wanted next, whether discovery should come as an option that is off by default, whether a follower should be allowed to send a few controls back, whether the manifest should cover all 16 decks (it covers the names of all decks and the cells of the active one), and whether the timeline position should be shared (a shared timeline belongs to prompt 33).
