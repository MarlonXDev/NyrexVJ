# ADR 0043: Release gates, a conditions block in every run report, and a compatibility matrix that keeps software OpenGL apart from real hardware

- **Status:** Accepted for the automated part (requested by MarlonXDev as prompt 18). Issue [#114](https://github.com/MarlonXDev/NyrexVJ/issues/114). The numbers of the gates are proposals, and no gate has been run on a real graphics card, a projector or Windows at run time.
- **Date:** 2026-11-25
- **Owners:** Maintainers (pending assignment)
- **Related:** [RELEASE.md](../RELEASE.md), [COMPATIBILITY.md](../COMPATIBILITY.md), [KNOWN_ISSUES.md](../KNOWN_ISSUES.md), [TESTING.md](../TESTING.md), [PERFORMANCE.md](../PERFORMANCE.md), [INTERFACES.md](../INTERFACES.md), [ADR 0027](0027-live-stability-and-hardware-test-matrix.md)

## Context
Every version so far was released after unit tests, self tests and a short soak run on one Linux container with a software renderer. [ADR 0027](0027-live-stability-and-hardware-test-matrix.md) added the hardware test matrix and the soak run, and said that a gate on frame times and a release checklist were a separate task. This is that task. The risk it addresses is that a green build reads as "works" when the only renderer that ever ran was llvmpipe, and that a measurement taken later cannot be compared because nobody wrote down the machine, the driver, the resolution or the clips.

## Findings (what existed before)
- **Existed:** the soak run (`--soak`) with samples, percentiles of the render time, frames over budget, missed frames, growth verdicts for process memory, the estimate of graphics memory, threads and handles, OpenGL error counts and a `passed` flag; `scripts/measure_live.py` for the outside view of processes and the card; the hardware matrix with automated and manual tests and a results file, refusing a hardware result whose environment names a software renderer; the unit tests and self tests in the continuous build; the check that a tag matches the version; the crash handler, the restart test and the media outage tests; the updater and its tests.
- **Existed, not enough:** the continuous build ran `--soak 6` and checked only that the output file was not empty, so a crash, an OpenGL error or a report that said `passed: false` could not fail it; a run report did not say which machine, driver, resolution, clips or effects it came from; the results file asked for an environment text but not for the driver, the clips or the duration; nothing said whether a report came from a software renderer except the person reading it; there was no check that the version in the build file, the changelogs, both READMEs and the decision table agree (a real drift was found earlier: the version in the build files lagged behind the changelog); tests for older and newer files were spread over several test programs.
- **Not found:** a release checklist, a document of compatibility by graphics card vendor and operating system, a list of known problems with steps to reproduce them, templates for a measurement and a log, a test that runs the program with clips that come and go, and any place where limits for frame times were written down.
- **Not verified before this version:** every manual test, a real graphics card, the program running on Windows, a driver reset, a monitor that is unplugged, and the real machine information on Windows.

## Decision
1. **Every run report carries a `conditions` block.** `--soak` (and the new media run) writes `schema` (`nyrexvj-run-report`, version 1), `kind`, and `conditions` with the system (operating system, version, architecture, processor, logical cores, memory), the build (version, build number, configuration), the graphics (vendor, renderer, the OpenGL version string as the driver, the shading language, the vendor of the card and the class), the resolution, quality, target frame rate, duration, scenario, and the names of the clips and effects that were in the composition during the run. The block is built in `core/run_conditions` (no OpenGL, unit tested) from a small `platform::systemInfo()`.
2. **The class of the renderer comes from its name and is conservative about what it calls hardware.** `software-gl` for llvmpipe, softpipe, swrast, lavapipe, software rasterizer, basic render, swiftshader and gdi generic; `virtual-gpu` for virgl, vmware, svga3d, virtualbox, vboxvideo, parallels, qxl and microsoft hyper-v; `gpu-reported` for everything else. The name `gpu-reported` says that the program saw a renderer, not that a person checked a card. A hardware result in the results file still needs a tester and a machine, and the matrix check refuses a hardware result whose system or driver names a software renderer or a virtual machine.
3. **A release gate in Python with the limits in a file.** `scripts/release_gate.py` reads a run report (and optionally the report of `scripts/measure_live.py`), judges it against `tests/hardware/gates.json`, prints a verdict for each gate, can write JSON and a Markdown summary, and exits 1 on any failure. Three profiles: `smoke` (every change, software OpenGL: crash exit code, a final report, no OpenGL error, no failed clip, a frame that is not stuck), `soak` (a long run on any renderer: the same plus growth), `hardware-release` (a real card: the same plus the percentiles of the work time of a frame against the frame period). The `hardware-release` profile refuses a run that is not `gpu-reported`. A value that is missing counts as a failure. The limits are proposals: P95 within one frame period, P99 within 1.5 periods, longest frame 100 ms, at most 2 percent of frames over a period, at most 0.5 percent missed frames, at least 97 percent of the target frame rate; growth limits are the ones the soak run already used.
4. **Software OpenGL is kept apart in every place a person reads.** The summary of the continuous build says "Software OpenGL only" in its first line and the gate banner repeats it; the artifact is named `soak-software-gl`; performance gates are skipped for software and virtual renderers with the reason printed; the vendor table in [COMPATIBILITY.md](../COMPATIBILITY.md) has a row for software OpenGL that counts automated checks and never hardware, and the rows of the cards count manual tests recorded on hardware.
5. **A media churn run.** `--soak-media FOLDER` imports the files of the folder, launches a clip on a layer every second second and clears a layer every ninth, and fails when a clip that should play has failed. It needs `NYREXVJ_DATA_DIR` to point at a scratch folder, because the import copies the files into the data folder; without it the option refuses to run.
6. **A consistency check for the release state.** `scripts/check_release.py` compares the version in `CMakeLists.txt` with the newest entry of both changelogs (and their dates and order), both READMEs, the decision table against the files of `docs/adr`, every command line option of `src/main.cpp` against the documents, every script and gate file a workflow names, and the release documents. `--release` also needs `KNOWN_ISSUES.md` to be checked at this version. It runs in both build jobs, and in release mode on a tag.
7. **Compatibility fixtures.** `nvj_compat_tests` loads files kept in `tests/data/compat`: files written by the code of 0.50.0 (frozen, and the test also checks the current writer produces the same JSON) and files in older shapes written by hand. Newer venue setups and controller profiles must be refused with their message. The older shapes were **not** written by older releases and the documents say so.
8. **The matrix gets an area and a stricter rule.** The area `release-quality` has eight automated checks and four manual tests (a hardware soak with the gate, a compatibility pass per card and system, a driver reset, video memory almost full). A hardware result must carry `conditions` with system, driver, resolution, clips, effects and a duration. A second table by card and system is generated into `COMPATIBILITY.md`.
9. **The manual workflow is manual.** `.github/workflows/soak.yml` runs only by hand with a length in seconds, builds without video, and judges the run with the `soak` profile. It has no schedule: a nightly job on software OpenGL would produce a green mark that means little.

## Alternatives considered
- **Frame time gates on the continuous build.** Rejected: llvmpipe renders at a few frames per second, so any limit would either always fail or be set so loose that it means nothing.
- **A threshold in the program that makes `--soak` exit with 1.** Rejected: the program should report, and the judgement belongs to something that can be changed without a rebuild and can be read by a person.
- **Detecting hardware by asking the driver for a vendor id.** Rejected for now: the renderer string is what OpenGL gives on every system, and a wrong guess toward `gpu-reported` is covered by the recorded tester.
- **A scheduled long soak.** Rejected, see decision 9.
- **One matrix table with the card as a column.** Rejected: it hides which cell is empty. A separate table keeps "no hardware run recorded" visible.
- **Storing older release files as fixtures by building old releases.** Not done: it needs old builds and an environment this project does not have. The hand written files say what they are.

## Consequences
- A pull request that changes a file format fails `nvj_compat_tests` until fixtures for the new version are written on purpose.
- A version bump that forgets a changelog, a README line or a decision row fails the build.
- Every future measurement can be compared, because it says where it came from.
- The summary of the build makes the limit of its own evidence visible every time.
- A run on Windows may report empty system information; that code has never run ([KNOWN_ISSUES.md](../KNOWN_ISSUES.md), KI-4).

## Validation / open questions
- **Run:** `nvj_release_tests` 56 checks, `nvj_compat_tests` 130 checks, `scripts/test_release_gate.py` 26 tests, `scripts/test_check_release.py` 15 tests, a 6 s soak and a 20 s media soak on llvmpipe through the `smoke` gate (both passed; 335 of 417 frames of a 30 s media run were over budget, as expected for software rendering), the video self test on 20 clips (all passed), the whole `ctest` suite.
- **Not done:** the `hardware-release` profile on any real graphics card (so its limits are unmeasured), the compatibility pass for any card vendor or system, the program on Windows, a driver reset, a monitor unplugged, VRAM nearly full, a hardware decoder, collecting files written by older releases, and a review by someone else.
- **Open for the maintainer:** the real limits of the gates; whether the manual soak workflow should also be offered for Windows (it needs a runner with a card, which the hosted runners do not have); whether a driver reset should be handled in the program; whether the checksum file and the tag check should also run `check_release.py --release` in the Windows job.
