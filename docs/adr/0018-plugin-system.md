# ADR 0018: Plugin system: a C interface for modulation sources and image sources, a time budget on a thread of its own, a marker and a safe mode list

- **Status:** Accepted (2026-11-21) as milestone 7 of [ADR 0012](0012-open-source-vj-platform-plan.md), implemented in v0.26.0. Issue [#53](https://github.com/MarlonXDev/NyrexVJ/issues/53).
- **Date:** 2026-11-21
- **Owners:** Maintainers (pending assignment)
- **Related:** [PLUGINS.md](../PLUGINS.md), [ADR 0014](0014-live-sources.md), [ADR 0017](0017-node-effect-editor.md), [PERFORMANCE.md](../PERFORMANCE.md), [INTERFACES.md](../INTERFACES.md), [DEPENDENCIES.md](../DEPENDENCIES.md)

## Context
NyrexVJ can be extended with shader clips, node effects, clip packs and OSC. None of them can bring in something that needs code: a sensor, a game controller, a network feed, a generator written in C or Rust, a picture made by another program's library. Resolume has a plug-in format for this and it is one of the reasons a VJ can stay in one program for a whole show.

Constraints that shaped the design:
- the program runs next to VRChat: a plugin must cost nothing until it is switched on and used, and must never be able to stop the picture,
- no new dependency: loading a library needs `dlopen` and `LoadLibrary`, which the program already uses for FFmpeg, NDI, PulseAudio and ALSA,
- a binary interface that outlives a compiler and a language: a C header with size-tagged structs,
- the program has to stay honest about what it can promise: native code in the same process can not be made safe against bad intent, only against mistakes,
- everything about a plugin that can be decided without running its code (the manifest, the version) is decided before its code runs.

## Decision
1. **A C header with a versioned ABI** (`plugins/include/nyrexvj_plugin.h`, version 1.0). Every struct starts with a `size` field that the writer fills and the reader checks, so fields can be appended in a minor version. The plugin exports one function, `nyrexvj_plugin_entry`, and fills a table with its id, name, version, number of sources (at most 8) and five functions: `get_source`, `create`, `destroy`, `modulation`, `frame`. The host gives the plugin a table with `log`, `get_audio`, `get_beat` and `get_parameter`. Two kinds of source exist: **modulation** (one float, about 60 times a second) and **frame** (1280 x 720, RGBA, 8 bits, straight alpha, about 30 times a second). Plugins get no OpenGL context, no window and no pointer to anything of the host except the table.
2. **A manifest before code.** `plugins/<folder>/plugin.json` (format `nyrexvj-plugin`, version 1) names the id, the API version and the library for each system. The manifest is validated (size, JSON, format, id, name, version numbers, library file name, file exists, unique id) and the API version is compared **before the library is opened**: the major version must be equal, the minor version at most the host's. A plugin that does not fit is listed with the reason and never loaded. At most 16 folders, 16 KiB a manifest.
3. **Off by default.** A plugin is loaded only after the person ticks it in Settings, Plugins (`plugins/config.json`), and `--no-plugins` switches the whole system off for a session. Nothing is opened, started or called for a plugin that is not enabled.
4. **Plugin code never runs on the render thread.** Opening the library and the entry call run on a loader thread. Each running source has a runner thread that calls `create`, then `modulation` or `frame` on a clock, and `destroy`. The render thread does three things only: publish a snapshot of audio and beat (a mutex that the plugin side holds for a copy), read an atomic value (`modulation`) or take the last frame (`LiveFrameBox`, as for NDI and cameras), and run the watchdog in `update()`.
5. **A time budget for every call, checked twice.** `modulation` 20 ms, `frame` 100 ms, `create` and `destroy` 500 ms, load and entry 1 s. The watchdog on the render thread compares the start time of the call that is running with its budget; a call that is over is **abandoned**: the plugin is marked Failed for the session, its sources stop, the thread is left alone and the show goes on. A call that returns but took longer than its budget fails the plugin as well. An error result is handled by the same path. A modulation that is not a number becomes 0 and is not a failure. The API version in the table that the entry function fills is checked again against the host and against `plugin.json`, so a library that reports another version than its manifest or than the host is refused after loading. A Failed plugin comes back only after a restart.
6. **Libraries are never unloaded.** An abandoned thread can return later into code of the plugin; unloading would turn that into a crash. The price is that a plugin can not be replaced while the program runs.
7. **The frame path checks what it can.** The runner gives the plugin a buffer with 64 guard bytes behind it and checks them and the fields of the image after every call; a plugin that writes behind the buffer or changes the description fails. The frame is copied into a `LiveFrame` and published to the same box as a camera, so the live input path (colour handling, upload, release after the idle time) is the existing one.
8. **Sources that nobody reads stop.** A modulation runner stops after 3 seconds without a read and starts at the next read. A frame source runs while its clip is on a layer and is released with the live path.
9. **Crash marker and safe mode.** Before a call into plugin code the runner writes the plugin id into a small table of fixed size (no allocation, signal safe); the crash handler writes the ids in the table as `plugin: <id>` lines into the crash report. At the next start `recordPluginCrashes` reads the report of the previous session and puts the ids into `plugins/disabled.json` **before the host loads anything**. The plugin is listed as Safe mode and comes back only when the person presses *Enable again*. A report without a plugin line records nothing.
10. **Integration.** Eight modulation slots appear as the audio bands `Plugin 1` to `Plugin 8` (after the timecode bands; presets store a band by its name, so no stored value changes meaning) and work everywhere that takes a band: modulations and effect reactions. Four frame slots give the clips `Plugin Source 1` to `Plugin Source 4` (a live clip kind that behaves like NDI and cameras). Each source has up to four parameters, sliders from 0 to 1, stored in `plugins/config.json`. The stage source list has a fixed size of 20 and is not extended; plugin bands are not available there. The band list in the UI shows `Plugin N` only when it is assigned or currently selected.
11. **A test of the whole path.** The example plugin (`plugins/example`, C99, no dependency) has one modulation source and one image source with parameters. The test plugin `tests/plugins/broken_plugin.c` is built 20 times with a mode that breaks one rule on purpose (see Validation). `--plugin-selftest FOLDER` loads a plugin through the real engine and checks both source kinds; CI runs it with the example plugin.

## Alternatives
- **A separate process for each plugin from the start.** This is the only way to survive a crash and to give a plugin fewer rights. Rejected for this milestone, as ADR 0012 already said: it needs shared memory frames, a protocol and a supervisor before there is one plugin. The interface is shaped for it (a plugin only sees the table and gets and gives plain data), so a host process can be put behind the same header later. Until then the page says plainly that there is no sandbox and that a crash in a plugin ends the program.
- **Running plugin calls on the render thread with a time check.** Rejected: a check afterwards can not stop a call that does not return, and the render thread is the one thing that must not wait.
- **Killing a stuck thread.** Rejected: there is no safe way to do it. A killed thread leaves locks and heap state of the plugin behind, so the thread is abandoned and the plugin switched off.
- **Letting a plugin draw with OpenGL.** Rejected: it would share the context with the render thread or need a second one, and a plugin that leaves the state changed breaks every effect. Frame sources give pixels and the program uploads them.
- **C++ classes in the interface.** Rejected: the layout and the names depend on the compiler and the standard library; a C struct table works from any language that can export a C function.
- **A scripting language inside the program (Lua, WASM).** Rejected for now: it would be a dependency, and a script is slower than native code for pictures. It could be a plugin.
- **A signature or an allow list for plugins.** Not done: there is no key system or trust model in the program, and a signature does not make native code safe. The protection is the off switch and the text that says what a plugin is.
- **Unloading a plugin when it is switched off.** Rejected (see point 6). A plugin that is switched off stops its threads and is not called again.
- **Plugins for effects or for the stage sources.** Not in this milestone: an effect plugin needs a way to run code on the graphics card without the risks above, and the stage source list is a fixed list that needs its own change.

## Consequences
- A person who enables a plugin gives it all the rights of the program. The Settings page says so in its first line, in every language.
- A plugin that crashes the program ends the show once. It is not loaded again until the person says so, so it can not take the program down at every start.
- A plugin that hangs costs one thread and one library mapping until the program is closed. A plugin that is started and fails over and over can not do that, because a Failed plugin stays off for the session.
- Image sources are 1280 x 720 and 30 fps for every plugin. The size is fixed so that the buffers and the upload are known; a plugin that wants another size has to scale itself. The limit constants (`NYREXVJ_PLUGIN_MAX_WIDTH` and `MAX_HEIGHT`) are in the header for a later version.
- Plugin bands share the eight slots. Two bands can point at the same source; they read the same value (one instance for each source key).
- The ABI is a promise. **Version 1.0 is not declared stable.** It is declared stable after one release of use with the example plugin and the broken plugin tests, as ADR 0012 said. Until then a minor version may still change what is documented as 1.0 if a mistake in the header shows up; the major number rises only for a break.
- Windows is built and tested by CI, but the plugin path was not run there by the maintainers.

## Validation
Tests (all run in CI):
- `nvj_plugin_tests` (294 checks, about 10 seconds):
  - manifest: scan, each refusal reason, id and library name rules, size limit, folder limit, duplicate ids,
  - **compatibility before code**: a plugin with the wrong major version and one with a newer minor version are listed as not compatible and are **never loaded** (the library of the test is a plugin whose load would crash the test, so a load would fail the test),
  - config and safe list: round trip, damaged and wrong format files, limits,
  - crash markers: the table is filled and emptied by calls, the report names the plugin,
  - the **example plugin** built by CMake and loaded by the test: modulation range and variation, parameters reach the plugin, the audio snapshot reaches the plugin, the frame source gives the right size, opaque pixels and a changing picture, the idle stop and the restart, enable and disable,
  - 20 broken modes: a **slow** modulation, a **hang** that never returns (the render thread keeps calling `update()` and keeps a bounded time per call), a **failing** call, a value out of range, failing `create`, failing entry, a missing entry function, duplicate source ids, an id that differs from the manifest, a slow load, an entry table that reports API 2.0, a source table with more than 8 sources, a source with no `modulation` function, a frame that changes the image fields, a frame that writes behind the buffer, a slow frame, a log that writes without limit (the limit is checked from the output of the program),
  - **a crash in a child process**: the test starts itself as a child (`--crash-child`), the plugin crashes it in `modulation`, in `create` and in the entry function (a null write), the crash report names the plugin, the next start puts it in safe mode, the host does not load it, `clearSafeMode` brings it back,
  - **the host stays responsive** while a plugin hangs or loads for a long time: the longest `update()` plus `modulation()` call on the test thread during a one second hang (and during a slow load) stays below 100 ms, and `stopAll` returns in under 100 ms while the hung thread is still alive.
- `--plugin-selftest` in CI (Linux), with the example plugin and the real engine: the modulation source gives values between 0 and 1 that change, the image source delivers 1280 x 720 frames through the live path, the clip `Plugin Source 1` is uploaded and lit, the call times are inside the budget, and no thread is left.
- address and undefined behaviour sanitizers for the plugin tests: 294 checks, no error from the host code. The only reports are the null write that the crashing test plugins make on purpose.

Measured on the maintainer's build machine, Linux, software OpenGL (Mesa llvmpipe), GCC 13, release build, one run of each:
- the example plugin through the engine (`--plugin-selftest`): modulation 82 calls in the test window, the slowest 0.013 ms (earlier run: 0.049 ms) against a budget of 20 ms; the image source delivers 30.5 frames a second (reported by the runner) at 1280 x 720, 99 % of the picture lit,
- a throwaway program (not in the repository) that links the core and calls what the render thread calls each frame (`publish`, `update`, and one `modulation` for each of the 8 slots), 200,000 frames, five runs: **0.05 to 0.06 microseconds a frame with plugins off and no slot read, 0.07 to 0.08 with 8 slots read, 0.06 to 0.08 with plugins allowed and nothing enabled, 0.16 to 0.21 with the example plugin running in two slots.** At 60 frames a second the last number is about 12 microseconds in a second. The example plugin's own thread adds about 60 calls of 0.01 to 0.05 ms a second,
- memory: a running image source holds about four to five frame buffers of 3.5 MiB in system memory and one 3.5 MiB texture on the graphics card; a modulation source holds nothing noticeable.

Not measured: the cost of a plugin that does real work; plugin sources next to VRChat; Windows at run time (`.dll` loading, the crash marker with the Windows handler); a plugin written in another language than C; the start time with many large plugins; plugins with long running threads of their own.
