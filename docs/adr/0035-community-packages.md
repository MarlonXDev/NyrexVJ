# ADR 0035: Community packages: install presets, shaders, node effects and plugins from a file

- **Status:** Accepted for the local part (requested by MarlonXDev as prompt 17). Issue [#98](https://github.com/MarlonXDev/NyrexVJ/issues/98). An **online catalogue, signing of packages, automatic activation of a plugin, automatic installation of dependencies and a package server are not built** and stay Proposed.
- **Date:** 2026-11-25
- **Owners:** Maintainers (pending assignment)
- **Related:** [PACKAGES.md](../PACKAGES.md), [SHOWS.md](../SHOWS.md), [INTERFACES.md](../INTERFACES.md), [ADR 0034](0034-show-packages.md), [ADR 0018](0018-plugin-system.md), [ADR 0026](0026-plugin-system-2.md), [ADR 0017](0017-node-effect-editor.md), [ADR 0022](0022-glsl-shader-2.md)

## Context
People who make presets, shaders, node effects or plugins for NyrexVJ had no way to hand them to somebody else except a folder of loose files and a description of where each file goes. The person on the other end had no way to see what a file would replace, whether it fits their version, or what a plugin could do. The task asked for a versioned manifest with metadata, licence, dependencies, compatible NyrexVJ versions, checksums and a preview; a local install and removal with a conflict check first; an online catalogue only as a separate optional proposal; and native plugins that are never activated or run without clear consent, with the existing security mechanisms and Safe Mode left as they are.

## Findings (what existed before)
- **Plugins** (ADR 0018, 0026) live in `plugins/<id>/` with a `plugin.json` that is parsed and checked before any library is opened. The user enables a plugin in the plugin settings, which writes `plugins/config.json`. A crash marker and the safe list (`plugins/disabled.json`) keep a plugin that crashed from starting again, and `--no-plugins` starts a run without plugins. There are 16 plugin folders at most, the id follows `validPluginId`, and a library has the extension of the platform.
- **Shader and node files** (ADR 0017, 0022) are plain files in `shaders/` and `nodes/`. The library names effects after the file name, so a second file with the same name hides the first.
- **Presets, venues and masks** are files in `presets/`, `venues/` and `masks/` that refer to each other by name only.
- **The `.nyxshow` container** (ADR 0034) already had: a stored (not compressed) layout, a manifest read from the end, plain names with a kind, SHA-256 per file, two phase writing with rollback and per-kind limits. It deliberately has no kind for plugins.
- There was no concept of an installed package, of a version of a file bundle, of a dependency between bundles, or of a record of which file came from where.

## Decision
1. **A second container, `.nyxpack`, built on the first.** It shares the reader and writer of `.nyxshow` and differs in magic (`NYXPACK` and `NYXPKEND`), manifest format name (`nyrexvj-pack`), the kinds it allows and its limits (256 MiB, 256 entries, 256 KiB manifest, JSON depth 12). `kindAllowedIn(format, kind)` makes the two formats refuse each other's content. A show package still cannot hold a plugin; a community package cannot hold media, models or scene packs.
2. **Three kinds are new:** `plugin` (only `plugin.json` and libraries with the platform's extension, 128 MiB, packages only), `preview` (a picture of at most 1 MiB, shown in the window and never installed) and `license` (a fixed name, `LICENSE.txt`, 64 KiB, stored next to the record).
3. **Metadata in the manifest, checked before use:** `id`, `packageVersion` (up to four numbers, nothing else, so two versions can always be compared), `author`, `description`, `license`, `homepage`, `nyrexvj.min` and `max`, `dependencies` (`id`, `min`) and `preview`. A dependency on itself or the same dependency twice is refused.
4. **Dependencies are checked, never fetched.** A package that needs another one installs only if the other is already installed in a version that is new enough. The installer also refuses an update that would leave an installed package without the version it needs, and refuses to remove a package that another one depends on. There is no solver and no network access.
5. **Install is a plan first.** `planInstall` returns the state of every file (new, update, same, identical, conflict, owned by another package, folder in the way, not for this platform) and a list of findings of three severities: **blocking**, **needs consent** and **notice**. `ready()` is true only with no blocking finding, with every consent given and with enough free space. The window and the command line run the same plan.
6. **A different file with the same name never gets overwritten silently.** The default is to block. The user picks Keep my files (theirs stays, the package's copy is skipped and said so) or Replace my files (theirs goes to the backup first). A file that another installed package owns blocks.
7. **Native plugins need consent and are never switched on.** A package with a plugin carries a consent finding that has to be ticked (`--pack-accept-plugin` on the command line). The plugin is copied to `plugins/<plugin id>/` and left **off**. The installer never writes `plugins/config.json`, the safe list or the crash marker, and it never loads the library; it reads `plugin.json` with the same parser the loader uses. A plugin must be off to be updated or removed. A plugin that was stopped for crashing stays blocked and the user is told.
8. **Updates and removals move, they do not delete.** Every file is written to a temporary name, checked by SHA-256, then moved into place. Replaced files and files the new version no longer has are first moved to `package_backups/<time>/`. Any failure puts everything back. A file the user changed after the install (its checksum no longer matches the record) is never moved; it is kept and reported.
9. **A record per package, `packages/<id>.json`** (`nyrexvj-installed-pack`), with the files and their checksums, the dependencies, the date and the NyrexVJ version of the install. It is the only way NyrexVJ knows what belongs to a package, so a removal can never touch a file that is not listed. A copy of the licence text is kept next to it.
10. **Shaders get a notice, not a block.** A shader runs on the graphics card, and the installer cannot judge it. The user is told once per package that shaders are code, and the existing shader checks (compile, `--check-shaders`, the last good version) stay as they are.
11. **Building a package is part of it.** A folder with a `pack.json` becomes a package in the Create tab or with `--pack-build`. Links and folders inside are left out and reported, files the kind does not allow are reported, and nothing is written until the folder is clean.
12. **The fingerprint is shown.** The SHA-256 of the whole package is on the screen so that a person who has an author's published value can compare. It is not a signature and the window says so.

## Alternatives considered
- **A ZIP file or a tar.** Same reasons as in ADR 0034: paths, links, compression and duplicate names.
- **A plugin that installs other plugins or has a store inside the program.** Would give code a way to bring in more code. Refused.
- **Switching on the plugin after the user ticked consent.** Consent to install is not consent to run. The plugin settings stay the single place where a plugin is enabled, and Safe Mode and the crash marker apply there.
- **An automatic dependency solver or a download of missing dependencies.** Needs a catalogue, a trust model and network access. Not asked for, and a wrong guess would change the user's files.
- **Overwriting by default with a backup.** Simpler, and wrong: the user did not ask for it, and a later restore of a backup is more work than choosing a policy once.
- **Putting package files in their own folder and loading from there.** The library, the node editor and the plugin loader read fixed folders. A new search path in each of them is a lot of change for little gain, and the record already says what belongs where.
- **Signing with a key of the maintainer.** Needs a key, a place to keep it and a rule for who may sign. Left to the maintainer.

## Consequences
- A package shares the file container with show packages, so every fix of the reader helps both. A change to `show_package.cpp` has to keep both test groups green.
- A plugin id from a package is checked with the plugin's own rules and cannot collide with another plugin folder.
- Two packages cannot hold the same file name for the same folder. That is on purpose; the installer says which package owns the name.
- `Limits::forPack()` is small on purpose. A package with a large plugin needs the 128 MiB per file and 256 MiB in total. Raising it is a one line change and a maintainer decision.
- New files: `docs/PACKAGES.md`, `src/core/pack_workflow.*`, `src/app/pack_dialog.hpp`, `src/app/ui_packs.cpp`, `src/app/pack_cli.*`, `tests/test_pack.cpp`. New data: `packages/`, `package_backups/`. New start options: `--community-packages`, `--pack-file`, `--pack-build`, `--pack-info`, `--pack-install`, `--pack-remove`, `--pack-accept-plugin`, `--pack-allow-downgrade`, `--pack-keep-mine`, `--pack-replace`, `--pack-overwrite`. 139 new texts in all seven languages and a new manual section in English and German.

## Validation / open questions
- Done here, on Linux with the Mesa software renderer: `nvj_pack_tests` (365 checks: versions, metadata, dependencies, version conflicts, update and downgrade, rollback after a failure, file paths and names, consent for native plugins, plugins left off, tampered, oversized, cut-off and incomplete packages), the changed `nvj_show_package_tests`, the whole suite, the translation check and the website check. The command line was run against a real package (install, install again, remove). The window was opened with `--community-packages` and looked at in screenshots.
- **Not done:** Windows beyond the CI build, an interactive click through of the window, a real plugin library inside a package (the tests use files that only look like libraries and never load them), packages of the maximum size, network drives and USB sticks.
- **Open for the maintainer:** whether packages should be signed and with what, whether an online catalogue is wanted (it needs a server, a trust model and a review process), whether `Limits::forPack()` is the right size, and whether a package may carry a language file or a colour theme later.
